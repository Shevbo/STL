Утренняя SMS о статусе запуска алготорговли STL. Заказ Бори 2026-07-21.

**Где крутится:** cron на **smain** (Europe/Moscow) → `~/bin/stl-morning-sms.sh <mode>`,
лог `~/stl-morning-sms.log`. smain выбран, потому что там garden SMS gateway + WG-доступ к
шлюзу + keymaster; заодно внешний вотчдог: ляжет hoster/STL — smain всё равно шлёт DOWN-SMS.

**Расписание (обновлено 2026-07-21, было одно `3 9 * * *`):** ДВА сообщения в день, режимы
`ready`/`takeoff` (аргумент скрипта). Будни: `50 6 * * 1-5 ... ready` + `3 7 * * 1-5 ... takeoff`.
Выходные: `50 9 * * 0,6 ... ready` + `3 10 * * 0,6 ... takeoff`. Префикс по режиму, ВЕРДИКТ
здоровья из статус-строки (`grep "торговля запущена"` → healthy). ready+ok = «К торговому дню
все системы STL готовы. <status>»; takeoff+ok = «Взлёт прошёл, полёт нормальный. <status>»;
если НЕ healthy — аффирмативный текст меняется на «ВНИМАНИЕ: ... НЕ готов / проблема на
взлёте». Старый скрипт в `~/bin/stl-morning-sms.sh.bak.<epoch>`.

**STL-часть (моя зона):** `hoster:~/stl-status-line.sh` минтит portal-токен (signer +
SHECTORY_AUTH_BRIDGE_SECRET), дёргает `/api/v1/quik/robots-mirror` +
`/api/v1/quik/agent-local-status`, печатает ОДНУ RU-строку. smain её забирает по `ssh hoster`.
Синхронизация с QUIK берётся из `recon.robot_checks[]` (`orders_ok`/`trades_ok`); реал/бумага —
из `agent-local-status robots[].mode` (флаг `paper` в mirror НЕнадёжен, у части None).
Пример: «STL 09:46: торговля запущена. агент на связи. Торгует роботов: 7 (4 реал/3 бумага).
Сверка с QUIK: 3/4. РАССИНХРОН: RIU6/l90z0a (сделки не сходятся).»

**SMS-шлюз (garden, зона Klod-Access):** sms-gate.app / capcom6, Android в WG `10.66.0.9:8080`.
Контракт из `smain:~/workspaces/garden-manager-app/src/lib/sms.ts`: `POST {URL}/message`,
`Authorization: Basic base64("user:pass")`, тело `{"message":..,"phoneNumbers":[phone]}`.
Секреты keymaster: `GARDEN_SMS_GATEWAY_URL` (база), `GARDEN_SMS_GATEWAY_AUTH` ("user:pass").
Cred-файлы: `~/.keymaster/credentials/garden_sms_gateway_{url,auth}`.

**Номер получателя:** keymaster `STL_SMS_PHONE` → `~/.keymaster/credentials/stl_sms_phone`
(Боря положил сам 2026-07-21). Скрипт молча выходит, если не задан.

**СТАТУС: работает end-to-end** (проверено 2026-07-21, http=202 state=Pending). ВАЖНЫЙ НЮАНС:
телефон-шлюз sms-gate.app был ОФЛАЙН 43 дня (WG-пир 10.66.0.9 без handshake) — значит и OTP
самого garden всё это время не слался. Боря перезапустил устройство, WG поднялся, SMS пошла.
Если шлюз снова отвалится (`timeout` на 10.66.0.9:8080 / 2.63.181.105:8080) — SMS встанет.
Непроверенный фолбэк: `SMSC_API_TOKEN` (smsc.ru, облако, не зависит от телефона) — контракт
уточнить у Klod-Access, если понадобится. Публичный IP шлюза `2.63.181.105:8080`, LAN `192.168.1.118`.

**Анти-ложная-тревога:** зеркало in-memory на миг пустеет при переподключении агента (видел
10:09 → «АГЕНТ НЕ НА СВЯЗИ, 0 роботов», через минуту снова 7 роботов). Поэтому сборщик на
hoster ретраит 3×/8с, и «ПРОВЕРЬ ТОРГОВЛЮ» шлётся только если пусто и после ретраев.

**«Итог вчера» — строгая бухгалтерия (2026-07-22, по требованию Бори: утренний
снапшот хрупок, в 6:50 идёт аукцион).** Итог дня фиксируется кроном hoster
`52 23 * * *` → `~/stl-day-close.sh` (сессия закрыта 23:50, QUIK на связи до
23:57): пишет запись в `~/.stl-day-close.jsonl` (одна на дату, rerun-safe) и
результат в `~/.stl-day-result.json`; SMS-строка читает результат ТОЛЬКО из
этого файла (date == вчера, иначе «н/д»). Метрика: primary = дельта equity
счёта из QUIK futures_limits (агент публикует acc_money: cbplimit+varmargin+
accruedint, комиссия ts_comission; ветка fix/tape-replay-gate fb585d1,
SCRIPT_VERSION 2026.07.22-replaygate2 — ЖДЁТ merge+publish+Stop/Start Lua);
fallback пока Lua старый = дельта суммы pnl_rub реал-роботов, в SMS с тильдой
«~». Ввод/вывод средств исказит equity-дельту того дня (не детектится).
Запись за 21.07 засеяна из 06:50-базы (realized не менялся за закрытую ночь).
Лог: `~/stl-day-close.log`.

**ВХОДЯЩАЯ КОМАНДА «Статус» (2026-08-11).** Оператор в дороге без интернета пишет SMS
«Статус» — в ответ прилетает тот же текст, что во втором утреннем SMS. Возможно потому, что
приложение SMS Gateway (v1.64) отдаёт ПРИНЯТЫЕ SMS по `GET /inbox` (поля id/sender/createdAt/
contentPreview); `/messages` — это только исходящие, инбокса там нет. Реализовано ОПРОСОМ:
`smain:~/bin/stl-sms-command.sh` по крону `*/2`, лог `~/stl-sms-command.log`, состояние
`~/.stl-sms-cmd.state`. Вебхуки у приложения есть (`GET /webhooks`), но принимающий URL должен
быть виден телефону — это отдельная служба на Pi; опрос дешевле, цена — задержка до 2 минут.
ОТКАЗ РАДИО = МОЛЧАНИЕ ОБОИХ КАНАЛОВ (12.08.2026, оба утренних SMS не пришли). Текст был
построен верно, но телефон вернул `RESULT_ERROR_GENERIC_FAILURE` в 06:50 и 07:03, а в 07:08
тот же путь доставил — то есть радио отказывало не меньше 13 минут (не блокировка и не
баланс: входящие всё это время приходили). Повторов не было вовсе, телеграм-фолбэк тем же
утром отдавал 503. Сделано: `send-sms.sh` повторяет 3 раза по 30с при `Failed` (при
`Pending`/таймауте НЕ повторяет — будет дубль), а `stl-morning-sms.sh` при полном провале
кладёт текст в `~/.stl-sms-pending.json`, и опрос команд (каждые 2 мин) дожимает отправку
2 часа. Судить о канале по одной попытке нельзя: он живёт в чужой сотовой сети.

ВТОРАЯ ЛОВУШКА ТОГО ЖЕ ВЕЧЕРА: у входящего id вида `text:<хэш>` зависит ТОЛЬКО ОТ ТЕКСТА.
Второй «Статус» приходит с ТЕМ ЖЕ id и заменяет первый в списке (число писем не растёт,
меняется только createdAt). Дедуп по id = одна команда за всю жизнь канала. Дедупить по
ВРЕМЕНИ: `last_cmd_ts`, планка двигается по всему ящику.

ЛОВУШКА, СТОИВШАЯ ДВУХ ЧАСОВ МОЛЧАНИЯ (11.08.2026): `GET /inbox` отдаёт ТОЛЬКО то, что
приложение уже втянуло в свой список. Пришедшая на телефон SMS сама туда НЕ попадает —
«Статус» лежал в системном инбоксе телефона два часа, а опрос читал список, где последнее
сообщение было от 5 августа, и честно писал NONE. Лечится `POST /inbox/refresh`
(`{"since":..,"until":..}` → 202, вебхуки не дёргает) ПЕРЕД чтением; он асинхронный, поэтому
в скрипте между refresh и GET стоит пауза. Судить о живости канала по «в инбоксе пусто»
нельзя вообще — сначала refresh.

Границы: канал ТОЛЬКО читающий (SMS подделывается, а на том конце реальные деньги), отвечаем
только на `stl_sms_phone`, команда «статус|status» целым словом, не старше 30 минут, не чаще
6 ответов в час, первый запуск лишь засевает состояние. Три цифры счёта (лимит откр., тек.
чист. поз., ВМ) даёт `hoster:~/stl-status-line.sh --money` — в первом утреннем SMS их нет.
