04.10.2026 оператор решил: воркер, который по просьбе правит код стратегии, живёт на smain (по образцу окна `stl-dev-spare`), результат принимает человек, после приёмки код идёт в прод. ui-ux построил сторону STL: `trader/api/lab_workbench.py` (таблицы `workbench_revisions` и `workbench_worker` создаются в lifespan `app.py` через `CREATE TABLE IF NOT EXISTS`, как `agent_tasks` — alembic в проекте нет), панель `WorkbenchPanel.svelte` на карточке витрины, контракт воркера разделом в `docs/backtest-workbench-spec.md`. Воркера пишет окно backtests по этому контракту.

**Решение, ради которого стоит помнить файл: воркер ходит по HTTP с отдельным токеном, а не в Postgres.** Исходная спека предлагала воркеру опрашивать очередь прямо в БД, как i9 опрашивает `agent_tasks`. Но i9 исполняет заданный код, а воркер исполняет ТЕКСТ, написанный моделью, и принимает сообщения оператора: при ошибке или инъекции в промпте реквизиты Postgres дали бы доступ ко всей базе (журналы сделок, заявки, сессии). Три ручки `worker/heartbeat`, `worker/claim`, `worker/revisions/{id}/report` с токеном `WORKBENCH_WORKER_TOKEN` позволяют ровно эти три действия. Токен не задан — ручки закрыты (503), а не открыты.

**Живость воркера — часть контракта, а не украшение.** Без воркера редакция встала бы в очередь и висела вечно, выглядя как «работает» — тот же класс ошибок, что молчащее зеркало терминала, выглядящее как флэт. Поэтому heartbeat раз в 30 с, `alive` = моложе 90 с; создание редакции без живого воркера отклоняется (409 `worker_down`), редакция в работе без воркера через 180 с уходит в `failed`, никакая не идёт дольше 2 часов. Фоновой задачи нет: проверка ленивая, на каждом обращении.

**Правила на сервере, а не на кнопках.** Переходы статусов — таблицей `TRANSITIONS` с ролью: воркер не ставит `accepted`, оператор не ставит `working`/`gates`/`ready`. `ready` невозможна при пустых или красных воротах, без diff и `code_ref`; зелёное — строго `ok is True` (строка `"true"` не считается). Одна рабочая редакция на карточку, новая только от последней (иначе две модели правят одну ветку). Принять можно только тот diff, который оператор видел: клиент присылает его sha256. Принимать вправе только список `STL_WORKBENCH_OPERATORS`; пустой список — принимать некому (приёмка ведёт к релизу, «по умолчанию все» недопустимо). API ничего не мержит и не релизит; слияние `wb/<card>/<rev>` в main делает окно backtests по явной команде оператора, воркер пушит только `wb/*`.

**Не проверено на живом Postgres (на 04.10.2026).** Базы в тестах нет, а гонять по боевой нельзя; 46 тестов покрывают правила на `MemStore`, доступ по HTTP, параллельные claim и таймауты, а SQL `PgStore` проверен только без базы (число `$n` равно числу параметров, имена колонок из белого списка, advisory-замок на каждой транзакции). Первый боевой запуск после рестарта `shectory-trader` — настоящая проверка; признак беды — `startup.workbench_schema_failed` в логе, ручки при этом отвечают 503, остальной API живёт.

**Открыто:** значения `WORKBENCH_WORKER_TOKEN` и `STL_WORKBENCH_OPERATORS` задаёт оператор; ручка `run` (прогон на i9) отвечает 501, пока backtests не пришлют формат задания; нумерации «ред.» витрины и рабочего места независимы, их надо свести, когда карточка станет «логика + инструмент».
