Связку OCO (стоп плюс следящий тейк от одного входа) терминал QUIK держит **одной** стоп-заявкой, и `brokerref` у неё — тег **одной** из ног. Книга STL при этом ищет запись по идентификатору той заявки, о которой думает сейчас, и за двое суток 01–02.10.2026 это дало три разных бага, последний — дубль защиты на живом счёте. Общее правило: всё, что сверяется со стоп-таблицей QUIK, обязано искать по СВЯЗКЕ, а не по id одной заявки.

Живой пример, на нём все три: вход `34593ce9df` купил 1 RIZ6, от него стоп `ae6731eec7` (уровень 85100) и следящий тейк `c21c114afa` (активация 86500). В терминале одна строка `310530617`, тег `stl-so-ae6731eec7`, `qty 1`, срабатывание 86500, заявка по 85080.

**Случай 1, ложная тревога (01.10).** Сверка книги с терминалом знала про ДОЧЕРНИЕ заявки и не знала про сиблингов по связке, поэтому вторая нога всегда выглядела беззащитной: «c21c114afa числится под охраной терминала, а записи в таблице стоп-заявок нет: позиция без сторожа». Защита была на месте. Ложная тревога про ОТСУТСТВИЕ защиты учит не верить тревогам, а ложный SMS по умной заявке в тот же день уже был. Фикс `9ca2442`: молчим, если живая строка есть у сиблинга по той же `oco_group`.

**Случай 2, ДУБЛЬ ЗАЩИТЫ (02.10, рестарт 08:00).** Держатель связки выбирался первым подходящим из детей, то есть ПО ПОРЯДКУ В КНИГЕ. Порядок не совпал с тегом записи → `rows.get(holder.so_id)` отдал `None` → ветка заключила «запись исчезла» → вернула охрану STL → следующий проход поставил ВТОРУЮ стоп-заявку. В журнале: `08:01:15 native_expired «снялась по сроку, сделок нет»`, `08:01:16 native_sent «защита отдана терминалу»`. В QUIK оказались `310530617` и `310530756` с одним тегом, одинаковые до копейки. Сработали бы обе — продали бы 2 контракта вместо 1. Фикс `cc8862c`: запись ищется по ЛЮБОЙ ноге, держателем становится та, чей тег на записи.

**Случай 3, тот же корень в показе.** Нативные стопы живут в ОТДЕЛЬНОЙ таблице и едут от агента отдельным сообщением (`StopOrderReport`, не в блоке `quik` зеркала) — экран «что стоит в QUIK» их не показывал вовсе, то есть не показывал ЗАЩИТУ ПОЗИЦИИ. См. [[reference-quik-stop-order-fields]].

**Как ловить:** появились две живые строки с ОДИНАКОВЫМ тегом и одинаковыми параметрами — это дубль, а не две защиты. Снимается по номеру: `POST /api/v1/quik/orders/terminal/cancel {"order_nums": [...]}` — ручка сама выбирает `KILL_STOP_ORDER` по полю `kind`. Послабления должны быть узкими: записи нет НИ ПО ОДНОЙ ноге — охрана честно возвращается STL, иначе повторится 23.09.2026, когда следящая продажа 30 контрактов пропала в терминале и книга похоронила её в `orphaned`.
