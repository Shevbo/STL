30.07.2026, при попытке дать роботу `lxk22…` (MACD RIU6) торговать 34 контрактами.

Числовые капы агента = **min(agent_config.json на VDS, пуш из STL)**, и
`Guard.ApplyPushed` (`quik_agent/internal/trade/limits.go`) — **CEILING-ONLY**:
живой пуш умеет только УЖЕСТОЧАТЬ. Более широкие значения агент читает
ИСКЛЮЧИТЕЛЬНО из своего файла при СТАРТЕ.

Отсюда практика:
- поднять env STL (`QUIK_MAX_CONTRACTS_PER_ORDER`, `QUIK_MAX_WORKING_CONTRACTS`)
  и перезапустить STL — НЕДОСТАТОЧНО: пуш выше текущего кап-значения молча
  игнорируется, `last_push_unix_ms` при этом обновляется (выглядит как «применилось»);
- рестарт агента поднимает капы только ДО значений его собственного файла;
- дальше упор в `agent_config.json` (ключи `max_contracts_per_order`,
  `max_working_contracts`), а VDS — зона оператора, SSH туда нет.

Замер того дня: env STL 18/20 -> подняли до 34/70, рестарт STL — эффективные
остались 18/20; рестарт агента (публикация rev 1785405699) — стали **20/20**,
то есть бэкстоп файла = 20/20. Оператор поправил файл на VDS, ещё один рестарт
агента (rev 1785406435) — стало **34/70**, и `lxk22…` получил max_position 34.

Как считать безопасный `max_position` робота при данных капах:
- заявка на выход — ОДНА на весь объём, значит `max_position <= max_contracts_per_order`;
- разворот держит в полёте выход + новый вход (`qty`), значит
  `max_position + qty <= max_working_contracts`.
При 20/20 и qty=2 безопасный максимум = **18** (не 20). Ставить больше = робот
наберёт позицию и не сможет выйти (тот же капкан, что 21.07).

Порядок правки, если капы поднимают: env STL + рестарт STL, ПОТОМ рестарт агента
(иначе агент стартует широким и тут же ужимается старым пушем). Рестарт агента
удалённо = публикация нового build_rev с триггером self-update.

Ещё: счётчик дневного лимита заявок живёт В ПАМЯТИ агента и обнуляется его
рестартом (после рестарта было 1/500 вместо 64/500).
