28.09.2026 оператор был уверен, что на торговой машине работает конфиг с одним
инструментом и снимком стакана раз в 5 секунд. По архиву шли ЧЕТЫРЕ инструмента
раз в 1.08 с. Причина (диагноз real-trade): на машине запущен скрипт СТАРШЕ
25.09, в котором ключей MD_BOOK_CODES и MD_BOOK_INTERVAL_MS не существует вовсе,
и стаканы идут по списку MD_CODES с интервалом 1000 мс. Правка, сделанная ради
того, чтобы сбой 25.09 не повторился, не работала с того самого дня.

Проверить версию работающего скрипта нельзя ни из одного окна разработки: Lua
пишет только в окно сообщений QUIK, SSH на машину нет. Единственный наблюдаемый
факт — сами данные. Замер: `python scripts/book_load_check.py --minutes 30`
(состав кодов, реальный интервал, доля от сломавшей нагрузки).

Арифметика, которая меняет решение: нагрузка это снимки в СЕКУНДУ, а не число
инструментов.

- 24.09 (6 кодов, интервал 1.22 с) = 4.91 снимка/с — на этой нагрузке 25.09 QUIK
  перестал отвечать серверу доступа, сессия рвалась каждую минуту, потеряно
  8 торговых часов архива;
- 28.09 до перезапуска (4 кода, 1.08 с) = 3.47/с, то есть 75% от сломавшей;
- 28.09 после перезапуска скрипта оператором (4 кода, 4.78 с) = 0.84/с, 17%.

Отсюда вывод, который снял спор: четыре инструмента раз в 5 секунд БЕЗОПАСНЕЕ,
чем один раз в секунду (0.8/с против 1.0/с). Держаться за частоту не нужно:
выжимка для i9 берёт ОДИН снимок в минуту, при 5 секундах используется один из
двенадцати.

**Why:** «на порядок ниже» было оценкой конфигурации, которая не запущена. Любое
утверждение о том, что собирается на торговой машине, проверяется замером по
архиву, а не чтением конфига.

**How to apply:** после любой правки подписок делать замер через минуту после
перезапуска и окном в 1 минуту, иначе смешается с дорестартным периодом.
