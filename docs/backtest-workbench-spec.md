# Рабочее место бэктеста в STL: редакции, чат с моделью, топ-100, честный объём (заказ оператора 04.10.2026)

Развитие витрины кампаний (`docs/campaign-showcase-spec.md`): карточка становится рабочим местом. Работа по
бэктесту переезжает на экран STL: график доходности на фоне «купил и держи», параметры прогона, чат с моделью,
история редакций. Это спека-предложение для ui-ux и backtests; решения оператора отмечены.

## Модель данных
- КАРТОЧКА = одна логика стратегии на одном инструменте. Переменные: период, параметры (ключи) стратегии.
  Нынешние карточки-кампании (шарды, разные стратегии/инструменты в группе) делятся на такие карточки;
  внутри карточки «разновидности» = прогоны.
- РЕДАКЦИЯ = неизменяемая запись `{id, card, rev, parent, created_by: operator|model, change_note,
  code_ref: git-ветка+коммит (null если код не менялся), params (центр и сетка), period, chat_ref, status:
  draft|queued|running|done|failed|accepted}`. Количество редакций не ограничено; рекурсия: новая редакция
  всегда создаётся из текущей открытой.
- ПРОГОН = задание на i9 (`agent_tasks`), запускает только оператор кнопкой на карточке. Расчёт НИКОГДА не в
  процессе STL API (правило изоляции).

## Экран карточки (весь экран)
1. Главное: большой график доходности на текущих параметрах, поверх него линия «купил и держи» на тот же
   инструмент, период и тот же полный объём; цвета: плюс мягкий зелёный, минус мягкий красный. Разность
   стратегия минус «купил и держи» показать вторым рядом.
2. Кнопка «Создать новую редакцию» открывает окно параметров прогона (период, ключи, сетка) и монитор.
3. Монитор: уже разработанный терминал STL (дизайн как у существующего монитора), чат с Claude через oauth-Lineman;
   фокус остаётся на графике, чат сбоку/снизу. Оператор просит внести условия, триггеры, правки; модель
   вносит их, создаёт новую редакцию в этой же карточке, UI переходит на неё, показывая параметры нового
   прогона и кнопку «Запустить прогон».
4. Таблица ТОП-100 по RF × net × L (решение оператора: RF = recovery factor, net = чистая прибыль, L = доля
   окон/месяцев в плюсе); показывает все три множителя в колонках; результаты каждого перегона карточки
   копятся (по всем редакциям карточки), с колонкой «редакция».
5. Цепочка редакций с `change_note` и ссылкой на коммит; переход между редакциями, сравнение двух.

## ЧЕСТНЫЙ ОБЪЁМ (жёсткое требование оператора)
- Все цифры без плеча: объём = число контрактов; ПОЛНАЯ стоимость = цена × стоимость пункта × контрактов
  (пик, не среднее; для переката по контрактам считается на момент максимальной позиции). Гарантийное обеспечение
  (ГО) нигде не используется: ни в доходности, ни в «на ГО».
- Доходность = net / пиковая полная стоимость. В карточке и в каждой строке топ-100 колонки: контрактов (пик),
  полная стоимость ₽, net ₽, доходность %.
- Кнопка «Нормализовать объём»: приводит карточку к стандарту 1 млн ₽ полной стоимости. Число контрактов
  `k = floor(1 000 000 / (цена входа × pv))`, минимум 1 (если контракт дороже 1 млн, показать «стандарт недостижим»
  и объём 1). Пересчёт для стратегий фиксированного размера = масштабирование pnl/кривой линейно (коммиссия и
  проскальзывание линейны по контрактам); для стратегий с ростом размера (мартингейл, добор) честный способ
  только перепрогон на i9 с новым базовым лотом: кнопка предлагает перепрогон и до его завершения показывает
  пометку «масштабировано, не пересчитано». Решает движок (backtests), не фронт.
- «Купил и держи» считается на тот же полный объём (то же число контрактов).

## Правка кода моделью: безопасность (решение оператора: ветка + тесты, без автослияния)
- Модель работает НЕ внутри процесса STL API: отдельный рабочий процесс (воркер) с чистым клоном репозитория,
  ветка `wb/<card>/<rev>`; STL монитор только передаёт чат и показывает статус.
- Разрешённые пути правки: `trader/lab/strategies/**`, `tests/lab/**`, описание параметров стратегии.
  Запрещено: `runtime.py`, `commission.py`, `smart_orders.py`, `robot_runner/`, `quik_agent/`, `proto/`, живые
  роботы, арминг, рестарты, секреты. Правка ядра `library.py`: только райдером с поведением по умолчанию побайтово
  прежним (правило проекта) и тестом на это.
- Обязательные ворота перед тем как редакция станет доступна для запуска: `pytest` затронутых модулей, `ruff`,
  тест «позиция на конец дня = 0 (включая короткие сессии выходных)», тест «без заглядывания вперёд» где
  применимо. Не прошло: редакция получает статус `failed` с логом, запуск недоступен.
- Код попадает на i9 из ветки (прогон берёт `code_ref`), в `main` только после явного «принять» оператором;
  `agent/update_manifest.txt` для новых модулей. Никакого scp в рабочую копию хостера; ветка пушится и
  подтягивается `git pull`.
- Все правки и чат сохраняются (`chat_ref`), у каждой редакции виден diff. Модель не заявляет вывод о кандидате:
  гейты и проверку fable по-прежнему делает окно backtests.

## Контракт воркера и ручек редакций (ui-ux, 04.10.2026, согласовано с backtests)

Реализация: `trader/api/lab_workbench.py`, тесты `tests/api/test_lab_workbench.py`. Таблицы
`workbench_revisions` и `workbench_worker` создаются при старте STL (`CREATE TABLE IF NOT EXISTS`,
как `agent_tasks`). Нужен рестарт `shectory-trader` (real-trade).

### Транспорт и доступ
Воркер на smain ходит НАРУЖУ по HTTPS на три ручки; в Postgres хостера доступа у него нет и не будет.
Заголовок `Authorization: Bearer <WORKBENCH_WORKER_TOKEN>`. Токен выдаёт оператор, лежит в keymaster
(в репозиторий и логи не попадает), на хостере читается из окружения STL. Токен не задан — ручки воркера
отвечают 503 (закрыто, а не открыто). Сессия оператора на этих ручках не принимается, токен воркера
на ручках оператора тоже.

Приёмка («accept») только для операторов из `STL_WORKBENCH_OPERATORS` (почты через запятую). Пусто —
принимать некому (503): приёмка ведёт к релизу, «по умолчанию все» недопустимо.

### Статусы и переходы (таблица на сервере, роль проверяется ею)
`queued → working` (только воркер, через claim) · `working → gates` (воркер) · `gates → ready` (воркер,
только при зелёных воротах и наличии diff и code_ref) · `working|gates → failed` (воркер, оператор,
система) · `queued → failed` (оператор: отмена; система) · `ready → accepted` (только оператор).
Воркер не может поставить `accepted`, оператор не может поставить `working`/`gates`/`ready`.
`draft` в перечне есть, но не создаётся: редакция рождается сразу в `queued`.

### Ручки воркера
**`POST /api/v1/lab/workbench/worker/heartbeat`** `{worker_id, version, busy_with?}` → `200 {ok:true}`.
Раз в 30 секунд, всегда, и когда занят, и когда свободен. `alive` у воркера = последний heartbeat моложе
90 секунд. `busy_with` — id редакции, которую он ведёт.

**`POST .../worker/claim`** `{worker_id}` → `200` задание или `204` (очередь пуста либо воркер уже ведёт
редакцию). Задание: `{id, card, rev, parent, message, parent_code_ref}`. `message` — текст оператора,
то есть НЕДОВЕРЕННЫЙ ввод для модели. `parent_code_ref` — ссылка на код предыдущей редакции карточки
(ветка + коммит), от неё строится `wb/<card>/<rev>`; `null` у первой. Claim сам считается heartbeat.
Работу ведёт ровно один воркер: пока он не закончил, новую ему не отдают.

**`POST .../worker/revisions/{id}/report`** `{worker_id, status?, log_append?, diff?, gates?, params?,
code_ref?, change_note?}` → `200 {ok, status}`. Все поля необязательны: можно слать только дописку лога.
- `status`: `gates` (правка сделана, идут ворота), `ready`, `failed`;
- `gates`: объект `{<имя>: {ok: true|false, ...}}`; `ok` строго булев `true`, строка `"true"` не считается;
- `ready` принимается только при непустых воротах, ВСЕХ `ok: true`, непустых `diff` и `code_ref`;
- `diff` хешируется (sha256), хеш показывается оператору, принять можно только его.
Коды ошибок (в `detail.code`): `not_yours` 403 (редакция выдана другому worker_id), `closed` 409
(редакция уже failed/ready/accepted, например оператор её отменил: воркер ОБЯЗАН остановиться),
`bad_transition` 409, `gates_not_green` 422, `no_result` 422.

### Что воркер обязан и чего не вправе
- Пушит ТОЛЬКО ветки `wb/*`; прав записи в `main` нет. Слияние делает окно backtests по явной команде
  оператора после «принять», с повторным прогоном тестов на слитом коде.
- Правит только пути из раздела «Правка кода моделью: безопасность». Ворота (pytest затронутых модулей,
  ruff, тест «позиция на конец дня = 0», «без заглядывания вперёд») отдаёт в `gates` по одному.
- Лог и diff уходят как ТЕКСТ и показываются как текст; ничего из них не интерпретируется.
- Живёт по heartbeat: нет heartbeat дольше 180 секунд при работающей редакции — она переходит в `failed`
  («воркер пропал»); никакая правка не идёт дольше 2 часов.

### Ручки оператора (экран)
`GET /status` (воркер: alive, возраст, версия) · `GET /cards/{slug}/revisions` · `GET .../revisions/{n}`
(статус, лог, ворота, diff, params) · `POST /cards/{slug}/revisions` `{message, parent?}` · `POST
.../revisions/{n}/cancel` · `POST .../revisions/{n}/accept` `{diff_sha}` · `POST .../revisions/{n}/run`
(пока 501: формат задания i9 определяет backtests).
Создание отклоняется (409 с кодом): `worker_down` (нет живого воркера), `busy` (в карточке уже есть
редакция в работе), `stale_parent` (страница устарела: редакция строится только от последней). Ограничения:
сообщение до 4000 знаков, лог до 1 МБ, diff до 1 МБ, ворота до 64 КБ.

### Открытый вопрос: два разных «ред.»
Нумерация редакций ВИТРИНЫ (`rev` в карточках сборщика, цепочка «ред. 1 → 2 → 3» линии идеи) и нумерация
редакций РАБОЧЕГО МЕСТА (эта таблица, начинается с 1 у каждой карточки) пока независимы. Когда карточка
станет «логика + инструмент», их надо свести в одну цепочку; как именно, решает backtests.

## Формат прогона редакции и одна нумерация «ред.» (backtests, 04.10.2026, ответ на открытые вопросы ui-ux)

### Прогон («run»)
Новый тип задания для i9 не нужен: прогон редакции = обычный `POST /api/v1/backtest/run` (тот же, что у
лаборатории и бэкфилла, `engine: "remote"`, считает i9 через очередь, на VDS запасной путь как сейчас).
Код редакции едет В ТЕЛЕ задания, поэтому ветку `wb/*` не надо доставлять на i9 и в `main` до приёмки:
- воркер в `report` кладёт `params` = `{script_code, base_params, param_sets? | params_grid?, symbol,
  date_from, date_to}`; `script_code` = ПОЛНЫЙ исходник файла стратегии на `code_ref` (до 256 КБ), обязан
  проходить `trader.lab.script_guard.validate_script` (это одно из ворот воркера: `script_guard: {ok: true}`);
- ручка `run` собирает тело `{scriptCode: script_code, baseParams: base_params, paramSets | paramsGrid,
  symbol, dateFrom: date_from, dateTo: date_to, engine: "remote"}`, ставит его тем же путём, что
  `/backtest/run`, и пишет id прогона (`backtest_runs.id`) в редакцию; повторный `run` = новый прогон, старые
  остаются; результаты = строки `backtest_results` этого `run_id`, кривые и сделки там же;
- предел комбинаций на один `run`: 2000 (сетка больше = отказ 422 `too_many_combos`); проверка
  `validate_script` повторяется в ручке (сервер не доверяет воркеру);
- статусы прогона берутся из `backtest_runs.status` как у лаборатории, отдельного состояния редакции нет.

Следствие для границ правки моделью: в рабочем месте модель правит ОДИН файл стратегии карточки (сам себе
модуль, импорты только `trader.lab.*` из `main`). Правки общих модулей (`library.py`, индикаторы, движок) в
рабочем месте недоступны: такой запрос воркер завершает `failed` с текстом «нужна правка общего модуля,
передано окну backtests».

### Одна нумерация «ред.»
Рабочее место работает только с карточками «одна логика + один инструмент» (после разрезки это все карточки
`kind: optimizer`; исследовательские карточки линий охватывают несколько инструментов, на них кнопка
«Создать новую редакцию» недоступна с причиной «карточка охватывает несколько инструментов»). Номер редакции
у карточки один: результат кампании, из которого выросла карточка, = ред. 1 (`rev` сборщика), первая редакция
рабочего места = ред. 2 с `parent` = 1, дальше по порядку. Сборщик витрины читает таблицу редакций через ручку
`GET /cards/{slug}/revisions` и показывает их в той же цепочке «ред. 1 → 2 → 3»; `rev` из сборщика и `rev` из
таблицы не пересекаются, потому что таблица начинает с `max(rev сборщика) + 1`.
