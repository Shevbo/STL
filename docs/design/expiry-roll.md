Проект, не код. Дата: 16.09.2026. Окно: real-trade. Статус: ждёт ответов оператора (раздел 12).

Никакого ИИ в контуре: обычная машина состояний, опрос зеркала агента, кнопки на экране.
Каждый факт ниже проверен по коду; что не найдено, помечено «ПРОВЕРИТЬ».

## 1. Модель процесса

### Сущности

Кампания (одна на серию и дату):

```
ExpiryCampaign {
  id: "RI-RIU6-RIZ6"            # серия-старый-новый, детерминированный = идемпотентность
  base: "RI", old: "RIU6", new: "RIZ6"
  last_trade_date: "2026-09-17"  # ISS LASTTRADEDATE старого
  deadline_ms                    # T-60 мин до конца торгов старого (раздел 12, вопрос 1)
  state: draft | checkup | exiting | switching | done | cancelled
  created_ms, updated_ms, cancelled_reason
  robots: [RobotRoll]
  events: [{ts_ms, robot_id|"", text}]   # хвост 200 записей, для экрана и SMS
  sms_queue: [{ts_ms, text, sent: bool}] # раздел 6
}
RobotRoll {
  robot_id, name, mode: real|paper, strategy_id
  state: selected | exit_wait | ready | switching | switched | refused | reset_needed | needs_operator | skipped
  position, working_orders, bars_count, paused   # снимок последнего такта
  exit_only_sent_ms, deploy_sent_ms, switched_ms, note
}
```

Состояния робота:

- `selected`: выбран, команд не было.
- `exit_wait`: `exit_only` поставлен, позиция или рабочие заявки ещё есть.
- `ready`: позиция 0, рабочих заявок нет.
- `switching`: отправлен `deploy-agent` с новым symbol, ждём подтверждения зеркала.
- `switched`: зеркало показывает новый symbol, `exit_only` снят.
- `refused`: раннер отклонил (позиция появилась между `ready` и деплоем) или зеркало не подтвердило за 2 попытки.
- `reset_needed`: бумажный робот на уже истёкшем контракте с позицией не 0 (выйти нечем).
- `needs_operator`: истёк таймаут ожидания, робот на паузе с позицией, реальный робот на истёкшем контракте с позицией.
- `skipped`: исключён оператором.

Переходы делает ТОЛЬКО такт кампании по фактам зеркала. Команды оператора (кнопки) меняют
`state` на `selected`/`skipped` или вызывают существующие маршруты (flatten, pause, set-position),
после чего такт сам увидит результат.

### Хранение

Один JSON-файл `data/expiry_roll.json` рядом с `data/smart_orders.json`, тот же образец
`SmartOrderBook.load/save` (переживает рестарт STL, без миграций БД). В файле не больше одной
активной кампании на серию; завершённые хранятся 30 дней для экрана истории.

БД не нужна: объём крошечный, читатель один (такт), писатель один (такт + маршруты через тот
же объект в `app.state`). Если позже понадобится история по годам, перенести в `agent_control`
(key/value) одной строкой на кампанию.

### Идемпотентность и рестарт STL

- Каждое действие выводится из ФАКТА зеркала, а не из «что я уже посылал»: `exit-only` можно
  слать повторно (тот же params с флагом), `deploy-agent` с тем же symbol у раннера = обычный
  редеплой без сброса баров (host.py: `rolled=False`, пауза сохраняется).
- После рестарта STL такт читает файл, для каждого робота не в терминальном состоянии
  пересчитывает состояние по зеркалу: symbol == new -> `switched`; symbol == old и
  `exit_only` в params и позиция 0 -> `ready`; и т.д. Отправленные, но не подтверждённые
  команды не помнятся, повторяются (безопасно).
- Зеркало пустеет на миг при переподключении агента (память: ретраи 3x8 с в SMS-скрипте):
  такт не переводит робота ни в какое состояние, пока зеркало не содержит его строку три
  такта подряд; отсутствие робота в зеркале > 10 мин = `needs_operator` с текстом
  «робот пропал из зеркала».
- Такт: раз в 5 с (как сторож умных заявок), только когда есть кампания в `exiting|switching`.

### Ручная отмена

Кнопка «Отменить кампанию»: state -> `cancelled`; для роботов в `exit_wait` снимается
`exit_only` (`exit-only on=false`), для `switching`/`switched` ничего не откатывается (робот
уже на новом контракте, обратный ролл только руками через тот же деплой). Отмена не отменяет
ручные сделки шага 3: они уже на бирже.

## 2. Выбор контракта

- Список серий = базы (`base_of`) всех symbol из зеркала роботов плюс коды из
  `health.positions[]` с `net != 0` (ручные позиции).
- `next_contract(old)`: среди строк `_securities()` с той же базой берём минимальную
  `LASTTRADEDATE`, строго большую `LASTTRADEDATE(old)`. Для RI: RIU6 (17.09) -> RIZ6 (17.12).
  Для BR (месячный): BRV6 -> BRX6, не BRZ6. Функция новая, живёт в
  `trader/quik/expiry_roll.py` и импортирует `base_of`, `_securities` из
  `trader/lab/contract_roll.py`. `_securities` приватная: письмо окну backtests с просьбой
  сделать её публичной (одна строка) или оставить импорт как есть по договорённости.
- Дата и время конца торгов старого: `LASTTRADEDATE` по ISS. ПРОВЕРИТЬ: торги в последний день
  у квартальных FORTS заканчиваются дневным клирингом 14:00 МСК; взять из
  `/iss/engines/futures/markets/forts/securities/{code}.json` (поле есть только для даты,
  время подтвердить по спецификации контракта или по `market_session` окнам того дня).
- Оператор видит: серия, старый, новый, дата, дней до экспирации, список роботов серии с
  режимом и позицией, ручная позиция по старому коду. Может снять галочки (`skipped`).
- Кампания создаётся заранее (за N дней, вопрос 8), а «Старт» переводит в `checkup`.

## 4. Шаг 1: «только на выход» и ожидание

- Для каждого робота `selected` -> `POST /robots/{id}/exit-only {on:true}` -> `exit_wait`.
  Маршрут берёт params из зеркала (мерж, не замена: критическая ловушка про `exit_only`/
  `allow_short`), поэтому кампания ничего не пересобирает.
- Такт: позиция 0 и `working_orders` пуст три такта подряд -> `ready`. Робот в `exit_wait`
  никогда не закрывается кампанией.
- Таймаут: `deadline_ms` (по умолчанию T-60 мин до конца торгов старого в день экспирации;
  до этого дня таймаута нет, роботы просто торгуют на выход). По истечении:
  `needs_operator`, тревога WARN `EXPIRY_EXIT_TIMEOUT` через AlertForwarder (Telegram) и
  строка в SMS-очередь, на экране кнопка «Закрыть по рынку» = существующий `flatten-agent`
  с вводом ID робота (реальные деньги, только руками). Напоминание повторяется каждые 15 мин
  до дедлайна и каждые 5 мин в последние 30 мин.
- Бумажный робот на УЖЕ истёкшем контракте (проверка 15): котировок нет, выйти нечем.
  Ветка `reset_needed`: кампания шлёт `pause-agent`, ждёт `paused` в зеркале, шлёт
  `set-position-agent {position:0, avg_price:0, confirm_id: robot_id}` (belief-only, реальных
  заявок нет), после позиции 0 в зеркале -> `ready`; после переключения `start-agent`, если
  робот не был на паузе до кампании. Для реального робота на истёкшем контракте с позицией:
  `needs_operator` с текстом «позицию по RIU6 биржа исполнит расчётом; закрой руками в QUIK
  до конца торгов, потом запиши сделку кнопкой «записать сделку» или обнули позицию».
- Робот без позиции с самого начала: сразу `ready` (exit_only всё равно ставится, чтобы он
  не вошёл в старый контракт в очереди на переключение).

## 5. Шаг 2: переключение и подтверждение

Переключаем роботов `ready` по одному (следующий после подтверждения предыдущего или через
60 с), чтобы раннер сохранял состояние по одному и отчёт группировался.

- Тело `deploy-agent` целиком из зеркала: `strategy_id`, `schedule`, `max_position`,
  `paper` = (`agent-local-status.robots[].mode == "paper"`, не флаг зеркала), `symbol = new`,
  `params = params из зеркала с symbol = new`. `exit_only` ОСТАЁТСЯ в params при деплое:
  если раннер отклонит ролл (позиция появилась), робот остаётся в режиме выхода, а не
  получает params без флага. Снимается отдельным `exit-only {on:false}` после подтверждения.
- Подтверждение (до 60 с, три такта подряд): зеркало `symbol == new`, `params_json.symbol
  == new`, `bars_count < 30` (у старого было до 600), `paused` как до деплоя, позиция 0.
  Затем `exit-only off` -> `switched`. При открытом рынке дополнительно за 3 минуты
  `bars_count` вырос хотя бы на 1, иначе тревога «бары по RIZ6 не идут» (фид), робот
  остаётся `switched`, но с пометкой.
- Отказ: зеркало через 60 с показывает `symbol == old`. Причины: (а) позиция не 0 (раннер
  пишет LIFECYCLE «ОТКЛОНЕНА» в журнал робота) -> обратно в `exit_wait`; (б) команда не дошла
  (переподключение) -> одна повторная попытка через 60 с, потом `refused` и тревога.
  Никаких штормов деплоя: не больше двух попыток на робота без нажатия оператора.
- Откат: не нужен. Раннер при отказе ничего не меняет; при успехе обратный путь = ещё один
  ролл руками (деплой со старым symbol), кампания его не делает.
- Регрессия 16.09 (агент обновился, раннер стартовал заново): такт продолжает сверять
  `symbol` и `bars_count` роботов `switched` до конца кампании. Если symbol снова `old` или
  `bars_count` прыгнул до сотен сразу после перезапуска раннера (`runner_report_age_ms`
  обнулился), робот -> `needs_operator`, CRITICAL `EXPIRY_ROLL_REGRESSED`, кнопка «пауза».
  С раннером f28f6b4 это не должно происходить, проверка остаётся как страховка.
- Прогрев: у нового контракта бары с нуля, стратегия с длинным окном не торгует, пока не
  наберёт. Это штатно (память `MACD warmup`); экран показывает `bars_count` и оценку
  «прогрев ~N мин» из параметров (slow/lookback), если известны. Досев баров кампания не
  делает (раннер при ролле сознательно не засевает).

## 6. Отчёты: SMS и компаньон

### SMS

STL SMS не шлёт и секретов шлюза не имеет; канал есть только на smain (WireGuard к телефону,
`send-sms.sh` с повторами, Telegram-дубль). Поэтому:

- STL публикует очередь: `GET /api/v1/quik/expiry/sms` -> `[{id, ts_ms, text}]` неотправленных,
  `POST /api/v1/quik/expiry/sms/ack {ids}`. Токен как у `stl-status-line.sh`.
- На smain новый скрипт `stl-expiry-sms-v1.sh` (имя с версией: правило оператора), крон
  `*/2` в торговые часы, как `stl-sms-command.sh`: забрать, отправить через `send-sms.sh`,
  подтвердить. Падение шлюза = тот же Telegram-дубль, что у утренних SMS. Задержка до 2 мин.
- Дубль каждого текста уходит немедленно в Telegram через `AlertForwarder` (код
  `EXPIRY_ROLL`, severity INFO; timeout и регрессия WARN/CRITICAL).

Группировка (чтобы не слать 20 SMS): такт копит события и формирует одно сообщение, когда
(а) прошло 10 минут с прошлого, или (б) событие срочное (timeout, регрессия, отказ), или
(в) кампания завершилась. Один робот упоминается один раз на переход.

Формат (кириллица = 70 символов на сегмент, лимит одного сообщения 280 символов = 4 сегмента,
лишние роботы заменяются счётчиком «и ещё N»):

```
STL экспирация RI 17.09 13:05. RIU6>RIZ6. Переключены 3/5: fvg-1, boll-2, ob-3.
Ждут выхода: usopen (поз -2). Отклонён: нет. Ручная: 4 RIU6 не переложены.
```

Финальное: `STL экспирация RI: готово 5/5, ручная переложена 4>4 RIZ6, 13:41.`
Срочное: `STL экспирация RI: usopen НЕ ВЫШЕЛ к 13:00 (поз -2). Закрой по рынку или руками.`

### Компаньон

Снапшот (`quik_companion.py`, блок `expiry`, только когда есть активная кампания):

```
expiry: { base, old, new, deadline_ms, state,
          robots: [{name, state, position, note}],
          manual: {old_net, new_net, state} }
```

Панель: карточка «Экспирация RI: RIU6 > RIZ6, до конца торгов 1 ч 12 мин», строка на робота.
Теги у робота в блоке роботов: `ждёт выхода` (жёлтый, поверх существующего «только на
выход»), `переключён RIZ6` (зелёный, 24 ч после `switched_ms`), `не вышел` / `отклонён`
(красный). `m.html` синхронно с `companion.html` (память reference_companion_market_bug).
В `_CONTROL_RULES` добавить иглу «экспирация» -> пометка «требует человека: открой экран
Экспирация в STL».

## 7. Шаг 3: перекладка РУЧНОЙ позиции (отдельная кнопка)

Реальные сделки. Ничего не делается без предпросмотра и подтверждения вводом кода
контракта.

- Ручная позиция = `health.positions[old].net` минус сумма позиций роботов по `old` из
  зеркала (то же, что `recon.manual.account_net`). Если роботы ещё в `exit_wait`, кнопка
  заблокирована с текстом: позиция счёта смешана с роботами, дождись их выхода.
- Спред-заявки в нашем пути нет (proto PlaceOrder), значит две ноги:
  нога A: закрыть N старого (side противоположна знаку net), нога B: открыть N нового
  (side по знаку net). Обе ставятся ОДНОВРЕМЕННО как маркетабельные лимитки через
  `/orders/place` (цена = ask/bid плюс подушка 2 шага, `quantize` по `price_step` из
  `smart_orders.py`, коллар из настроек), кусками не больше `max_contracts_per_order`.
  Альтернатива по выбору оператора: обе ноги через `/start-execution` (доводка мейкером с
  `worst_price`), дешевле по спреду, дольше и с риском не набрать (вопрос 5).
- Предпросмотр: N, стороны, цены обеих ног из `health.feed`, базис (new.last - old.last),
  ориентировочная стоимость = спред обеих ног в рублях (через `step_cost`) + комиссия
  тейкера (`trader/lab/commission.py`), ГО после = `N * margin(new) * множитель`, свободно
  `money.planned`, что станет с защитой (список умных и стоп-заявок к переносу).
- Контроль исполнения поштучно: `client_id` с префиксом `xr:<campaign>:<A|B>:<chunk>`,
  состояние из `OrderStore` (`/orders/working`, поля filled/remaining/state/text) и
  `ExecutionUpdate` для доводки. Экран: две строки прогресса, «A 3/4 исполнено, B 4/4».
- Частичное исполнение: пока |filledA - filledB| > 0 экран красный «дисбаланс K контрактов»
  и кнопка «довести остаток» (повтор недобранной ноги только на разницу, снова с
  подтверждением). Автоповторов нет. Через 60 с неисполненный остаток снимается `/cancel`
  и остаётся дисбаланс на решение оператора.
- Отказ (TransReply с ошибкой, `state=rejected`): текст QUIK на экран, вторая нога, если ещё
  не исполнена, снимается `/cancel`; если исполнена, показать дисбаланс.
- Перенос защиты после `filledB == N`:
  умные заявки книги по `old` (`active()`): для каждой создать копию на `new` с уровнем,
  сдвинутым на базис и приведённым к сетке, старую отменить (`DELETE /{so_id}`) только после
  того, как новая принята. Оператор в предпросмотре галочками выбирает, что переносить.
  Нативные стоп-заявки QUIK по `old` (`/stop-orders`): `stop-kill` старых и `stop-place` новых
  с тем же сдвигом. Этап 2, после серий на GZ (память: механика не проверена), до тех пор
  экран просто перечисляет их с текстом «перенеси стопы в QUIK руками».
- Запреты по времени (`market_session` + окна дня): рынок открыт и `phase == trading`; до
  конца текущего окна больше 5 минут (клиринг 14:00 и 18:50, конец сессии 23:50); после
  открытия окна прошло больше 2 минут (аукцион, память reference_smart_order_phantom_fire);
  в день экспирации только до `deadline_ms`. Лента свежая (проверка 11). Kill-switch снят,
  главный флаг включён с обеих сторон, оба кода в белых списках, дневной лимит не выбран.
- Бумажной ручной позиции не бывает: шаг 3 только для реальных денег.

## 11. Тестовый план

Детерминированные (pytest, без сети и агента):

- `next_contract`: фикстура строк ISS: день экспирации (RIU6 LASTTRADEDATE == today) даёт
  RIZ6; BR месячный BRV6 -> BRX6; серия без следующего -> None; `front_contract` в тот же день
  возвращает RIU6 (фиксируем, почему он не годится).
- Машина состояний на фейковом зеркале: selected -> exit_wait -> ready -> switching ->
  switched; отказ раннера (symbol остаётся old) -> exit_wait; две неудачные попытки ->
  refused; пауза с позицией -> needs_operator; истёкший контракт бумажного -> reset_needed
  -> ready; таймаут -> needs_operator и одно срочное SMS; мигание зеркала (пустой отчёт один
  такт) не меняет состояний.
- Рестарт STL: сериализация в JSON и восстановление состояний из зеркала (робот уже на new
  -> switched без повторного деплоя).
- Регрессия 16.09: после `switched` зеркало показывает symbol old и bars_count 600 при
  обнулившемся `runner_report_age_ms` -> needs_operator, CRITICAL, деплой не повторяется сам.
- Чекап: каждая из 17 проверок на словарях статуса: зелёная и красная ветка, текст
  инструкции содержит код контракта.
- SMS: группировка (5 роботов за 10 минут = одно сообщение), лимит 280 символов с «и ещё N»,
  срочное уходит вне окна, робот упоминается один раз на переход.
- Шаг 3 (чистая логика): расчёт ручной позиции (счёт минус роботы), предпросмотр (цены,
  сетка, ГО), запреты по времени на границах окон (13:59:30 запрещено, 14:06 разрешено,
  первые 2 минуты после открытия запрещено), дисбаланс после частичного исполнения, отказ
  одной ноги снимает другую, перенос умной заявки со сдвигом на базис и квантованием.
- Регрессия зон: `exit_only` остаётся в params при деплое и снимается только после
  подтверждения; тело деплоя из зеркала не теряет ни одного ключа params.

Прогон на бумажных роботах (без денег, при агенте на связи):

- Кампания только из бумажных роботов серии с ближайшей экспирацией; пройти чекап
  (ожидаемо красные 6-7 до правки белого списка), шаг 1-2, увидеть теги в компаньоне и SMS
  на телефоне оператора. Перезапустить shectory-trader посреди `exiting`: кампания
  продолжается. Попросить оператора перезапустить раннер посреди `switching`: робот на новом
  контракте, bars_count с нуля.

Реальные роботы: только при операторе, по одному, первый с позицией 0. Шаг 3: первый раз на
GZ по 1 контракту (как серии стоп-заявок), потом на боевой серии.

## 12. Вопросы оператору

1. Дедлайн выхода: T-60 мин до конца торгов в день экспирации (14:00 -> 13:00) или раньше
   (например, вечер предыдущего дня)? Роботы, не вышедшие к дедлайну: оставить на старом
   контракте до расчёта биржей или всегда закрывать по рынку руками?
2. Переключать робота сразу, как вышел в ноль (может быть за несколько дней до экспирации,
   ликвидность уже в новом), или ждать общего окна переключения?
3. За сколько дней до экспирации создавать кампанию по умолчанию (2 для квартальных, 1 для
   BR)? Нужен ли автоматический черновик с напоминанием в SMS утром?
