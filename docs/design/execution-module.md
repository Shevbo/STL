# Исполнительный модуль (проект, 15.09.2026)

Статус: проектирование. Ничего не реализовано, не задеплоено. Автор: окно real-trade.

## 0. Зачем

Инцидент 15.09.2026, 07:00 МСК. Ручная умная заявка trail_tp buy 5 RIU6 (активация
86900, откат 50) жила в процессе STL на хостере. Цена держалась 86860 несколько секунд,
сторож (1 с, last из change-gated тиков агента) пробой не увидел. В 07:28 догонялка по
свечам ISS (задержка ~15 мин, `catch_up_trail`) активировала заявку задним числом, и она
тут же купила по рынку 87450: на ~580 пунктов хуже плана. Книга STL записала среднюю
87442, QUIK показывает 87450.

Корень: сторож и исполнитель стоят не там, где данные и заявки. Путь «QUIK -> Lua ->
агент -> gRPC -> STL -> сторож 1 с -> gRPC -> агент -> Lua -> QUIK» проигрывает по
задержке и умирает вместе с STL или связью. Роботы уже живут на агенте и от STL не
зависят; ручные умные заявки должны жить там же.

Требования оператора (по смыслу):

1. Один исполнительный модуль для ЛЮБОГО потребителя: роботы и ручные умные заявки.
2. Задержка от события рынка до заявки в QUIK: миллисекунды, максимум единицы секунд.
   Задержка более 10 с на любом звене = тревога.
3. Сторож и исполнение умных заявок на QUIK VDS. STL только ставит и смотрит; упал STL
   или связь, заявки продолжают стеречь и исполняться.
4. Параметр агрессивности исполнения (4 режима, см. раздел 5) и тревога, если стоп или
   тейк не исполнился (мигание в компаньоне).
5. Цена входа в книге обязана совпадать с QUIK.

## 1. Что есть сейчас (по коду, не по памяти)

Агент (Go, `quik_agent/internal/trade/manager.go`):
- `PlaceOrder` / `CancelOrder` / `ReplaceOrder` (нативный MOVE_ORDERS, одна транзакция
  без окна «снял-поставил»), `KillSwitch`. Все размещения проходят Guard: master-флаг,
  белый список, per-order, working, daily cap. Коллар проверяется только в `sendMove`
  относительно текущей цены заявки; в `CheckPlace` коллара нет.
- Уже есть мейкер-цикл `execution.go` (`StartExecution`): дочерние заявки, локальный
  стакан, перестановка MOVE_ORDERS при уходе тача на шаг, анти-дребезг 200 мс, коллар
  worst_price. Используется только для ручных явных заявок, роботы его не трогают.
- `OnTrade` накапливает VWAP реального исполнения по заявке (`tradeAvg`), и
  `emitOrderUpdate` отдаёт его вместо лимитной цены, когда сделки уже были.
- Таблица рабочих заявок агента в памяти: рестарт агента её теряет
  (`docs/architecture.md`, «does NOT persist its own working-order table»).
- `staleAckTimeoutMs` = 20 с: PENDING без order_num помечается REJECTED, тревога
  `QUIK_NO_REPLY`.

Lua-мост (`quik_agent/lua/shectory_trade.lua`):
- Котировки `getParamEx` LAST/BID/OFFER раз в `MD_INTERVAL_MS` = 500 мс; стакан
  `getQuoteLevel2` на 10 уровней раз в 1000 мс; обезличенная лента `OnAllTrade` буферится
  и сбрасывается каждые 300 мс; таблицы счёта раз в 2 с.
- Лента: строка `{price, qty, side, receipt_ms, exch_ms}`; REPLAY GATE отбрасывает сделки
  старше `TAPE_GATE_SEC` = 300 с по биржевому времени (реплей после рестарта QUIK).
  Проверить: доходит ли пятый элемент `exch_ms` до Go (`bridge.go` case "tape" передаёт
  `ev.Trades` как есть, формат строки на стороне Go не проверял).
- Биржевое время сделки собирается через `os.time` из `datetime`: секундное разрешение.
  Миллисекунды (поле `datetime.mcs` или `ms` в QLua) не читаются: проверить.
- Транзакции: `NEW_ORDER` (TYPE L или M), `KILL_ORDER`, `MOVE_ORDERS`. `NEW_STOP_ORDER`
  в коде НЕТ (упоминается только как «v2» в runbook).
- Тег владельца заявки едет в `CLIENT_CODE` (20 символов), возвращается как brokerref в
  acc_ord/acc_trd.

Раннер (`robot_runner/runtime.py`): сам считает маркетабельную цену (BUY по ask, SELL по
bid при свежей котировке <10 с, иначе кросс 0.3%), сам ждёт встречную заявку 5 с
(`_CROSS_WAIT_SEC`), шлёт `PlaceRunnerOrder`; агент квантует цену к шагу
(`runner/server.go snapToStep`). Позицию и P&L ведёт по `OrderUpdate` с префиксом `rr:`.

STL (`trader/quik/smart_orders.py` + `trader/api/quik_smart_orders.py`): чистый
`evaluate()` (sl/tp/trail_tp/trail_sl/on_fill, OCO, защитные пары, маркетабельная цена с
подушкой 0.05..0.15%, квантование, свежесть тика 30 с, гейт сессии по ISS-оракулу),
сторож 1 с, orphan-логика, поиск цены сделки по acc_trd (`_fill_price`, `_match_trades`),
догонялка ISS раз в 5 мин. Тревоги: `AlertForwarder` в Telegram, CRITICAL дублируется
SMS. Компаньон опрашивает `/snapshot` раз в 5 с, тревоги рисует красным/зелёным
(`.alert`), мигания нет.

## 2. Где что живёт

| Компонент | Где | Почему |
|---|---|---|
| Сторож триггеров (sl/tp/trail/on_fill/OCO) | Go-агент, новый пакет `internal/smart` | Данные (лента, стакан, OnTrade) уже здесь, задержка до QUIK локальная |
| Исполнитель (машина состояний режимов 1..4) | Go-агент, расширение `internal/trade` (`execution.go` уже половина работы) | Один путь для роботов и ручных; Guard, MOVE_ORDERS, OnTrade VWAP уже здесь |
| Книга умных заявок (персистентная) | Go-агент, файл рядом с `robots` store | Переживает рестарт агента и STL |
| Постановка, отмена, мониторинг, история | STL (`trader/api`), зеркало книги агента | STL = пульт, не исполнитель |
| Стратегии роботов | Раннер, без изменений логики | Раннер шлёт НАМЕРЕНИЕ (сторона, объём, режим), цену считает агент |
| Тревоги | Агент `Alert` -> STL `AlertForwarder` -> Telegram/SMS + snapshot компаньона | Существующий путь |

Живучесть:

- Упал STL: агент стережёт и исполняет; при переподключении отдаёт STL полное
  состояние книги (как `RobotStatusReport`). Поставить новую заявку без STL нельзя
  (пульт мёртв), это честно и так.
- Упала связь: то же. STL показывает «агент не на связи, книга по состоянию на T».
  Отмена из STL при обрыве невозможна; кнопка отмены в UI это говорит.
- Упал агент: роботы и умные заявки стоят, как сегодня стоят роботы. Отдельно
  рабочие заявки в QUIK остаются; при старте агент восстанавливает книгу из своего
  файла и сверяет детей по brokerref-тегу через acc_ord/acc_trd (публикуются каждые 2 с).
  Заявка со статусом «исполняется», чей ребёнок в QUIK не найден, получает
  `orphaned` и тревогу; авто-перевзвода нет (цена другая, решает человек).
- Рестарт QUIK: лента реплеится. Сторож НЕ стреляет по сделкам, чьё биржевое время
  старше `TRIGGER_MAX_AGE_MS` (предложение 5 с) относительно часов агента, и молчит,
  пока `exchange_lag_ms` (уже считается по pong `last_trade_ts_ms`) больше того же
  порога. Lua-гейт 300 с остаётся вторым поясом.

## 3. Источник цены срабатывания

Триггер ТОЛЬКО по реальной сделке из `OnAllTrade` (лента), как у стоп-заявок QUIK.
Не по `getParamEx LAST` (он переиздаёт нерыночные значения вне сессии: инцидент
06.08, покупка 19 RIU6 в аукционе по цене, которой не было) и не по mid стакана.

Условия срабатывания на одной сделке (все обязательны):
1. Сделка пришла из ленты, инструмент совпадает.
2. `now_agent - exch_ms <= TRIGGER_MAX_AGE_MS` (5 с). Секундное разрешение биржевого
   времени даёт погрешность до 1 с, это учтено в пороге.
3. Гейт сессии: STL раз в час пушит агенту расписание торговых окон на сегодня и
   завтра из ISS-оракула (`market_session.py`, уже есть); агент кэширует его на диске.
   Сделка вне торгового окна не триггер. Расписания нет (агент долго без STL): гейт
   деградирует до «лента жива: были сделки с биржевым временем в последние 5 с».
   Аукцион открытия сделок не даёт, значит триггеров в нём не будет и без расписания.
4. Kill-switch агента не включён (как сегодня в STL: заявки остаются armed).

Трейлинг: пик ведётся по каждой сделке ленты, а не по снапшоту раз в секунду.
Экстремум внутри секунды больше не проскакивает. Пик персистится в книге агента.

Задержка от сделки до решения: буфер Lua до 300 мс + loopback. Если оператор
попросит ближе к «миллисекундам», снижать `md_pump` порог сброса ленты до 100 мс
(правка Lua = рестарт скрипта оператором). В v1 не трогать: 300 мс укладывается в
требование «единицы секунд», а Lua-правка требует отдельного окна обслуживания.

Догонялка по ISS (`catch_up_trail`) удаляется без замены: с лентой на агенте пропуск
пробоя возможен только при мёртвом агенте, и тогда честный ответ «пропущено, решает
оператор» (уже есть ручная активация `/activate`).

## 4. Единый путь исполнения: «намерение»

Все потребители шлют агенту одно и то же:

```
ExecIntent {
  client_id        // владелец: rr:<robot>:... для роботов, so:<id> для ручных
  code, side, qty
  purpose          // ENTRY | EXIT   (EXIT = стоп, тейк, flatten, выход робота)
  mode             // 1..4, см. раздел 5; EXIT принимает только 1 и 2
  worst_price      // опционально, жёсткий потолок цены (по умолчанию коллар 0.2%)
}
```

- Ручная умная заявка = триггер + ExecIntent. Сработал триггер, сторож отдаёт intent
  исполнителю на том же агенте, без сети.
- Робот: `PlaceRunnerOrder` получает новые поля `purpose` и `mode` (proto-расширение,
  обратно совместимо: старый раннер шлёт цену, `mode=0` = сегодняшнее поведение,
  маркетабельная лимитка по цене раннера). Раннер перестаёт сам считать цену и ждать
  встречную заявку: и то и другое переезжает в исполнитель. `purpose` раннер знает
  (уменьшает позицию = EXIT).
- `mode` робота задаётся ключом `exec_mode` в `params_json` (MERGE, не REPLACE, по
  правилу редактирования параметров), по умолчанию 1.

Исполнитель отдаёт наверх ОДИН агрегированный `OrderUpdate` по client_id родителя:
quantity = qty намерения, filled = сумма, price = VWAP по OnTrade, state по правилам
раздела 6. Дочерние заявки в QUIK могут меняться (MOVE даёт новый order_num), раннер и
STL этого не видят и не меняются. Это главное условие, чтобы раннер остался как есть.

## 5. Режимы агрессивности

Цены везде квантуются к шагу (`snapToStep`, у агента есть `PriceStep`) и не выходят
за коллар агента. «Свой уровень» = сторона нашей заявки: для BUY уровни bid, для SELL
уровни ask. «Уход цены» = наш уровень перестал быть тем, на который ставились
(тач ушёл на >= 1 шаг), с анти-дребезгом 200 мс, как в `execution.go decide`.

| Режим | Поведение | Итог при неисполнении |
|---|---|---|
| 1 «по рынку» | Лимитка, пересекающая спред: BUY по ask + подушка, SELL по bid - подушка (подушка 0.05%, мин. 3 шага, макс. 0.15% под коллар 0.2%), как сегодня `marketable_price`. Не `TYPE=M`: рыночная заявка не имеет цены, коллар её не ограничивает | Не налилась за `MARKET_FILL_TIMEOUT` (10 с) = переставить на новый тач ещё раз, затем тревога |
| 2 «первый уровень» | Ставим на лучший свой уровень (мейкер). Ушла цена: MOVE_ORDERS на новый лучший уровень. До 5 перестановок подряд; шестая = режим 1 | По цепочке в режим 1 |
| 3 «третий уровень, терпеливо» | Ставим на 3-й свой уровень стакана. Ждём 5 мин. Не налилась (цена ушла или стоит): MOVE на текущий 3-й уровень. Так 3 окна по 5 мин (15 мин), затем режим 2 | Режим 2, затем 1 |
| 4 «третий уровень, только вход» | Ставим на 3-й свой уровень, ждём 15 мин. Не налилась: снять, уведомить. Только `purpose=ENTRY`; для EXIT агент отвергает intent с текстом причины | Отмена + тревога INFO |

Частичное исполнение: остаток продолжает в том же режиме с тем же счётчиком;
MOVE_ORDERS с qty=0 сохраняет остаток (Lua «qty 0 => keep»). Заявка считается
исполненной при filled = qty.

Перестановки идут MOVE_ORDERS, а не «снял-поставил»: одна транзакция, без окна с двумя
живыми заявками, и MOVE не расходует daily cap (`CommitPlace` только в `PlaceOrder`).
Эскалация в режим 1 тоже MOVE на пересекающую цену; коллар в `sendMove` считается от
текущей цены заявки, для уровней 1..3 это заведомо внутри 0.2%.

Стоп и тейк (EXIT) по умолчанию режим 1. Режим 2 для EXIT допустим, но с бюджетом:
не налилось за 10 с суммарно = принудительный режим 1 независимо от счётчика
перестановок. Режимы 3 и 4 для EXIT запрещены на уровне валидации intent.

Комиссия: режим 1 = тейкер (биржевой сбор + брокер), режимы 2..4 = мейкер (только
брокер, `trader/lab/commission.py`: maker fee 0). Режим влияет на модель комиссии в
журнале: сегодня ledger и раннер считают всё тейкером; после внедрения флаг «как
исполнилось» (taker/maker) должен ехать в `OrderUpdate`/ledger, иначе отчёт врёт в
пользу режима 1. Отдельная задача, зона ledger.

## 6. Машина состояний одного intent

```
NEW ──валидация Guard/purpose/mode──> REJECTED (причина в text)
 │
 ▼
WAIT_CROSS   свои встречные заявки по инструменту (все владельцы, книга Manager)
 │           ещё в рынке: ждём до 5 с, затем шлём как есть (QUIK ответит «кросс
 │           блокирован» -> RETRY_CROSS: повтор, когда встречная сошла)
 ▼
QUOTING(level, moves, window)  ребёнок в QUIK; события: OnOrder/OnTrade/таймер/лента
 │  ├─ fill  -> filled==qty ? DONE : QUOTING (остаток)
 │  ├─ уход цены и moves<лимит -> MOVE, moves++
 │  ├─ moves==лимит -> ESCALATE (режим-1 цена через MOVE)
 │  ├─ окно истекло (режим 3) -> MOVE на текущий 3-й уровень, windows++;
 │  │        windows==3 -> режим 2
 │  ├─ окно истекло (режим 4) -> CANCELLING -> CANCELLED (+уведомление)
 │  ├─ EXIT и прошло 10 с без полного исполнения -> ESCALATE + CRITICAL
 │  ├─ QUIK reject (не кросс) -> REJECTED + тревога
 │  └─ no ack 20 с (SweepStale) -> REJECTED + QUIK_NO_REPLY (уже есть)
 ▼
DONE(avg_price = VWAP OnTrade, filled, taker|maker, метки времени)
```

OCO: у сработавшей умной заявки родственники по `oco_group` снимаются в момент
перехода её intent в QUOTING (не DONE): иначе пока стоп исполняется, тейк может
сработать тоже и открыть позицию в обратную сторону. Это уже так в `evaluate()`.

Защитные «блоки после сделки» (sl_offset/tp_offset/trail_after): создаются на агенте
при первом филле родителя от VWAP и filled qty, затем при каждом следующем филле
пересчитываются (уровень от VWAP, объём = filled), пока армированы. Это
`rebase_protective` сегодняшнего кода, только без опоздания на секунды и без
поиска цены по acc_trd.

Кросс-заявки: исполнитель единственный видит все рабочие заявки счёта, поэтому
ожидание встречной (`_CROSS_WAIT_SEC` раннера) переезжает сюда и действует и для
ручных, и для роботов, и между ними (робот-шорт против ручного лонга на одном
инструменте сегодня никак не согласован).

## 7. Бюджет задержек и тревоги

Метки времени на одном intent (все по часам агента, кроме первой):

| Метка | Что | Бюджет | Тревога |
|---|---|---|---|
| t_exch | биржевое время сделки-триггера | | |
| t_seen | сделка дошла до сторожа | t_seen - t_exch <= 2 с (300 мс буфер + loopback + разрешение 1 с) | > 10 с = WARN `FEED_LAG`, триггеры молчат (раздел 3) |
| t_sent | `sendTransaction` отправлен | t_sent - t_seen <= 50 мс (Lua poll 10 мс) | > 10 с = CRITICAL `EXEC_STALL` |
| t_ack | OnTransReply/первый OnOrder | t_ack - t_sent <= 3 с (по коду «QUIK acks in ~1s») | > 10 с = WARN, 20 с = `QUIK_NO_REPLY` (есть) |
| t_fill_first / t_done | первая и последняя сделка | режим 1: <= 10 с | EXIT не закрыт за 10 с = CRITICAL `EXIT_NOT_FILLED` (режим 5 оператора) |
| t_stl | состояние дошло до STL | <= 5 с при живой связи | > 10 с = WARN «зеркало отстаёт», только в UI |

Цель сквозная: t_sent - t_exch < 1 с в норме.

Куда идут тревоги: `Alert` агента -> STL `AlertForwarder` (Telegram, CRITICAL с SMS) ->
snapshot компаньона. В snapshot добавляется `alerts.flash: [{code, text, ts_ms}]`:
неснятые CRITICAL кодов `EXIT_NOT_FILLED`, `EXEC_STALL`, `SMART_ORPHANED`. Компаньон
(`frontend/public/companion.html`, опрос 5 с) мигает шапкой (CSS keyframes) пока список
непуст; снятие = клик по тревоге -> `POST .../alerts/ack`. Exe компаньона не
пересобирается. STL сегодня хранит принятые Alert-кадры только для пересылки:
проверить, есть ли в `app.state` их хранилище для UI, иначе завести (зона ui-ux).

Метрики для панели: гистограмма t_sent - t_exch и t_ack - t_sent за день по каждому
intent, в статусе агента (`status_snapshot`) и в карточке умной заявки в STL.

Часы: VDS синхронизируется `w32tm` раз в час; при дрейфе > 2 с показатели лага
недостоверны (уже есть `driftBad` на странице агента), тревоги по лагу в этом
состоянии помечаются «ненадёжно», но триггеры не отключаются.

## 8. Цена исполнения: один источник правды

Правда = сделки QUIK по нашей заявке, событие `OnTrade` (qty, price) по order_num.
Агрегация: VWAP = sum(price*qty)/sum(qty) по всем OnTrade всех дочерних order_num
одного intent (MOVE даёт новые номера, исполнитель их знает). Раннер уже получает
этот VWAP в `OrderUpdate.price`, STL-книга будет получать его же в состоянии умной
заявки. Никто ниже по течению не пересчитывает цену по acc_trd (`_fill_price` и
`_match_trades` в STL удаляются).

15.09 сделки 4 x 87440 + 1 x 87450 дали среднюю 87442. РЕШЕНИЕ ОПЕРАТОРА: цены вне
сетки шага (у RI шаг 10) не существуют и нигде не показываются и не используются.

Правило сетки (действует уже в STL, коммит d4908f6, и переносится на агент 1:1):
- цена входа = VWAP, округлённая по шагу в ХУДШУЮ для позиции сторону (покупка
  вверх, продажа вниз): 87442 -> 87450;
- уровни стопа/тейка/трейла считаются ТОЛЬКО от округлённого входа и сами лежат на
  сетке (86950 / 88450), никаких 86942;
- точный VWAP допустим лишь внутри денежного учёта (algo_trades считает по сделкам),
  на экран и в уровни он не выходит.

## 9. Риски и ограничения

- Коллар 0.2%: маркетабельная подушка макс. 0.15% (запас). Быстрый рынок: тач ушёл
  дальше подушки за время ack, заявка легла лимиткой. Режим 1 после 10 с переставляет
  ещё раз (MOVE к новому тачу) и только потом тревожит.
- Капы агента: пуш из STL только ужесточает; расширение только `agent_config.json` при
  старте (память «Капы агента = бэкстоп»). Умная заявка на qty > per-order cap
  отвергается ПРИ ПОСТАНОВКЕ (сегодняшнее поведение STL сохраняется, проверка
  дублируется на агенте). Daily cap: перестановки MOVE его не тратят; эскалации тоже
  MOVE. Робот-исполнитель, который вместо одной заявки ставит цепочку, cap не
  увеличивает.
- 32-битный QLua: все epoch-ms в `%.0f`; новые поля (метки времени intent) агент
  считает сам, Lua не трогаем. Единственная правка Lua в v1: НЕТ. Милисекунды сделки
  ленты и ускорение сброса буфера: v1.1, отдельный рестарт скрипта оператором.
- Реплей ленты после рестарта QUIK: два гейта (Lua 300 с, сторож 5 с) плюс молчание,
  пока `exchange_lag_ms` > 5 с. Тест обязателен.
- Дата сделки QUIK = торговый день (вечерка датирована завтра): для триггеров
  используется `exch_ms` из `datetime`, это реальное время, не торговая дата.
  Не смешивать с журналом (`journalsync`).
- Комиссия за скальпинг: модель завышает сбор на оборотистых днях; режимы 2..4
  делают это заметнее. Учётная задача, не блокер.
- Агент восстанавливает детей по тегу CLIENT_CODE (20 символов): формат `so:<id>`
  уместится, но проверить, что brokerref действительно возвращается для ручного
  класса (для `rr:` роботов возвращается, по коду журнала).
- Нативные стоп-заявки QUIK (`NEW_STOP_ORDER`, срабатывание на сервере брокера)
  в v1 не используются: режимы 2..4 ими не выразить, а дублировать стоп и нативной
  заявкой и агентом = риск двойного исполнения. Как «ремень» на случай смерти
  агента: возможно в v2 стоп-заявка QUIK на уровне хуже нашего на N шагов. Вопрос
  оператору.
