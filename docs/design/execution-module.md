Раннер (`robot_runner/runtime.py`): считает маркетабельную цену сам, ждёт встречную

раз в 5 с, мигания нет.

## 2. Архитектура: три яруса

| Ярус | Что делает | Живёт без |
|---|---|---|
| Сервер брокера (стоп-заявки QUIK) | Стережёт условие (стоп, тейк, трейл, связка, по исполнению) и при активации сам выставляет лимитную заявку по заданной цене | STL, агента, терминала, связи |
| Агент (Go + Lua на VDS) | Ставит и снимает стоп-заявки по команде STL или робота; зеркалит `stop_orders`; после активации ДОВОДИТ ребёнка (режимы 2..4, гэп, эскалация, таймауты); ставит защитную связку после входа; оценивает ГО; ограничивает частоту транзакций; наблюдатели и тревоги; заявки роботов | STL, связи |
| STL | Пульт: постановка/отмена через агента; экран: зеркало, наблюдатели, тревоги; компаньон | ничего не стережёт |

Правило стыка: ДО активации всё делает QUIK, агент только смотрит. ПОСЛЕ активации
ребёнок = обычная лимитка агента. Если ребёнок налился сам (режим 1), агент только
записывает цену и ставит защитную связку.

Живучесть:
- Упал STL/связь: стоп-заявки стерегут на сервере; агент доводит и ставит защитные
  связки; при реконнекте отдаёт STL зеркало и журнал переходов. Новую поставить нельзя.
- Упал агент: стоп-заявки стерегут и активируются; ребёнок ставится QUIK по цене из
  стоп-заявки без доводки. Цена в стоп-заявке для выходов всегда маркетабельная:
  режим 2 вырождается в режим 1 (РЕШЕНО 13). Мёртвый агент = тревога `AGENT_DOWN`
  со стороны STL (сторож молчания уже есть, коммит 5dba243). После старта агент
  читает `stop_orders`/`orders` и восстанавливает книгу по brokerref-тегу.
- Упал терминал QUIK: стоп-заявки на сервере брокера продолжают стеречь (по
  документации; сверить на GZ). Реплей ленты после рестарта QUIK не влияет.

## 5. Режимы агрессивности, доводка и гэп

Цены на сетке шага, внутри коллара. «Свой уровень» = сторона нашей заявки. «Уход
цены» = тач ушёл на >= 1 шаг, анти-дребезг 200 мс.

| Режим | Нативно (цена фиксируется ПРИ ПОСТАНОВКЕ) | Агент после активации |
|---|---|---|
| 1 немедленно | `PRICE` = `STOPPRICE` минус подушка (sell) / плюс (buy); `SPREAD` = подушка. Подушка 0.05%, мин. 3 шага, макс. 0.15% под коллар 0.2%. Не `MARKET_*` | Налился: ничего. Не налился за 10 с: гэп-режим (ниже) или MOVE к тачу с подушкой |
| 2 первый уровень | Вход: `PRICE` = `STOPPRICE`. Выход: `PRICE` маркетабельная как в 1 (мёртвый агент = режим 1, РЕШЕНО 13) | Вход: MOVE на лучший свой уровень, до 5 перестановок, шестая = режим 1. Выход: то же, суммарно не дольше 10 с, затем режим 1 |
| 3 третий уровень терпеливо (ENTRY) | `PRICE` = `STOPPRICE` | MOVE на 3-й уровень; 5 мин; MOVE на текущий 3-й; 3 окна; затем 2, затем 1 |
| 4 третий уровень, только вход (ENTRY) | `PRICE` = `STOPPRICE` | MOVE на 3-й уровень; 15 мин; `KILL_ORDER` + INFO |

Перестановки только `MOVE_ORDERS` (одна транзакция, daily cap не тратится). Каждая
перестановка = транзакция класса B у ограничителя (раздел 11).

Доводка при гэпе (РЕШЕНО 12). Гэп = в момент `CHILD_SEEN` тач на нашей стороне хуже
`STOPPRICE` больше, чем на `gap_detect_pts` (пример: стоп sell 86900, bid 86500 =
гэп 400). Ребёнок с подушкой (86770) не в рынке и висит. Вместо немедленного рынка
агент ждёт откат в нашу пользу, но под тремя ограничителями; нарушение ЛЮБОГО =
немедленно MOVE к тачу с подушкой (рынок):

| Параметр | Смысл | Пример (лонг 5 RIU6, стоп 86900, открылись 86500) |
|---|---|---|
| `gap_max_loss_pts` | максимальный дополнительный убыток от цены открытия гэпа (первая сделка после активации, `gap_open`) | `gap_open` 86500; при last <= 86500 - N сразу рынок |
| `gap_max_wait_sec` | максимальное время ожидания отката с момента `CHILD_SEEN` | по истечении рынок, где бы цена ни была |
| `gap_min_bounce_pts` | минимальный откат от экстремума с момента активации, при котором выходим | экстремум 86450, ребёнок MOVE на 86450 + M и едет за экстремумом вниз (как тейк-профит наоборот); коснулись = налился |

Логика: `GAP_WAIT`: ребёнок стоит на `extreme + gap_min_bounce` (sell), при новом
экстремуме MOVE вниз (транзакция класса A); наблюдение по локальной ленте/стакану.
Выход из режима: филл; или `last <= gap_open - gap_max_loss` -> рынок; или таймер ->
рынок. Значения по умолчанию: вопрос оператору (раздел 18, В18). Для покупки
зеркально. Гэп-доводка только для EXIT; вход при гэпе идёт по своему режиму.
Наблюдатель `gap_wait` пишет каждый переход.

Пример 15.09 в схеме: `TAKE_PROFIT_STOP_ORDER` buy 5 RIU6, `STOPPRICE=86900`,
`OFFSET=50`. Сервер брокера в 07:00 видит 86860, активирует, ведёт минимум, при
откате 50 ставит покупку сам. Агент видит ребёнка по `OnStopOrder` и при режиме 2
переставляет к bid до 5 раз. Ни STL, ни лента агента, ни расписание не участвуют.

Комиссия: режим 1 тейкер, 2..4 мейкер (`trader/lab/commission.py`). Флаг taker/maker
в `OrderUpdate`/ledger: отдельная задача.

## 6. Машина состояний доводки одного ребёнка

```
ARMED (стоп-заявка на сервере; агент зеркалит stop_orders, наблюдатели сверяют)
 │ OnStopOrder: активирована, linkedorder=N   (снята не нами -> WITHDRAWN/EXPIRED, раздел 10)
 ▼
CHILD_SEEN(N)  берём N под управление (робот/flatten: NEW_ORDER -> CHILD_SEEN)
 │  ├─ гэп обнаружен и EXIT -> GAP_WAIT (раздел 5) -> филл | рынок
 │  ├─ OnTrade/OnOrder: filled==qty -> DONE
 │  ├─ режим 2..4: MOVE по правилам, счётчики moves/windows
 │  ├─ EXIT и 10 с без полного исполнения (вне GAP_WAIT) -> рынок + CRITICAL EXIT_NOT_FILLED
 │  ├─ режим 4 и 15 мин -> KILL_ORDER -> CANCELLED (+INFO)
 │  ├─ отказ QUIK на ребёнке (ГО, планка, кросс) -> REJECTED + CRITICAL
 │  └─ ребёнок исчез из orders без сделок -> ORPHANED + тревога
 ▼
DONE(VWAP по OnTrade, filled, taker|maker, метки времени)
 │ ENTRY с блоками после сделки -> NEW_STOP_ORDER связки от округлённого VWAP
```

Кросс-заявки: перед `NEW_ORDER`/`MOVE` на встречной стороне агент смотрит свои
рабочие заявки по инструменту (все владельцы), снимает свою встречную того же
владельца, иначе ждёт до 5 с; отказ «кросс» повторяется, когда встречная сошла.
Ред. 5: ожидание встречной ДРУГОГО владельца вынесено в состояние WAIT_CROSS перед
`NEW_ORDER` (раздел 19.2), а зачёт двух намерений роботов происходит ещё раньше, в
NET_HOLD (раздел 19.3): NET_HOLD -> WAIT_CROSS -> CHILD_SEEN.

OCO внутри связки решает сервер; между независимыми стоп-заявками OCO нет, форма STL
предлагает связку.

## 7. ГО: отказ при постановке и ранняя диагностика

РЕШЕНО 15: стоп-заявка, выводящая потенциальное ГО за 100% доступного, НЕ ставится;
агент отвечает отказом `GO_EXCEEDED` с расчётом, STL показывает красным.

Оценка на агенте (каждые 2 с по acc_money/acc_pos):
- потенциальная позиция по инструменту = нетто + qty всех активных стоп-заявок и
  рабочих лимиток, УВЕЛИЧИВАЮЩИХ |позицию| (выходы не считаются);
- потенциальное ГО = сумма |потенциальная позиция| * `BUYDEPO` *
  `QUIK_MARGIN_MULTIPLIER`; доступно = `cbplplanned` + `cbplused`;
- > 80% = WARN `GO_NEAR_LIMIT`; постановка сверх 100% = отказ `GO_EXCEEDED`; текущее
  состояние сверх 100% (рынок ушёл, ГО выросло) = CRITICAL с перечнем стоп-заявок,
  которые не пройдут.

Когда сам QUIK/брокер проверяет ГО у стоп-заявки (постановка или активация): сверить
на GZ. Отказ ребёнка при активации «не хватает средств» = `STOP_CHILD_REJECTED_GO`
CRITICAL с флэшем. Оценка приблизительная (без неттинга и скидок), достаточно
«увидеть раньше».

## 8. Цена исполнения: один источник правды

Правда = сделки QUIK по нашей заявке, событие `OnTrade` (qty, price) по order_num.
Агрегация: VWAP = sum(price*qty)/sum(qty) по всем OnTrade всех дочерних order_num
одного intent (MOVE даёт новые номера, исполнитель их знает). Раннер уже получает
этот VWAP в `OrderUpdate.price`, STL-книга будет получать его же в состоянии умной
заявки. Никто ниже по течению не пересчитывает цену по acc_trd (`_fill_price` и
`_match_trades` в STL удаляются).

15.09 сделки 4 x 87440 + 1 x 87450 дали среднюю 87442. РЕШЕНИЕ ОПЕРАТОРА: цены вне
сетки шага (у RI шаг 10) не существуют и нигде не показываются и не используются.

Правило сетки (действует уже в STL, коммит d4908f6, и переносится на агент 1:1):
- цена входа = VWAP, округлённая по шагу в ХУДШУЮ для позиции сторону (покупка
  вверх, продажа вниз): 87442 -> 87450;
- уровни стопа/тейка/трейла считаются ТОЛЬКО от округлённого входа и сами лежат на
  сетке (86950 / 88450), никаких 86942;
- точный VWAP допустим лишь внутри денежного учёта (algo_trades считает по сделкам),
  на экран и в уровни он не выходит.

`STOPPRICE`/`STOPPRICE2`/`PRICE` защитной связки = округлённый вход плюс/минус
смещения; агент квантует до транзакции. Наблюдатель `grid` проверяет каждую цену
сделки и каждую цену в `stop_orders` на кратность шагу (раздел 10).

## 9. Что остаётся агенту как сторожу

Для `sl`/`tp`/`trail_tp`/`trail_sl`/связки/`on_fill` условие проверяет сервер
брокера: ни расписание, ни свежесть ленты агенту не нужны. Агент сам смотрит на

1. Доводка ребёнка (режимы 2..4, гэп): локальный стакан (`getQuoteLevel2` раз в 1 с,

## 10. Наблюдатели

Нативные механики QUIK не тестированы: каждое допущение раздела 3 накрыто
наблюдателем. Все живут в агенте (`internal/observe`), читают только события и
таблицы (транзакций не порождают), пишут журнал `observe.jsonl` на VDS (ротация по
дню), шлют `Alert` в STL, отдают состояние в `status_snapshot` и `StopOrderReport`.
Управление (РЕШЕНО 23): наблюдатели = QA-инструмент, вкл/выкл ТОЛЬКО в
`agent_config.json` (`observers.<name>: false`, читается при старте и по команде
`RELOAD_CONFIG`). Из STL наблюдателей не трогают. В настройках STL один переключатель
режима журнала `log_mode`, агент получает его командой `SetLogMode`:
- `verbose`: журнал всех событий плюс записи наблюдателей;
- `short`: только ключевые события (постановка, активация, филл, снятие, отказ, тревога);
- `no`: журнал не ведётся.
Тревоги наблюдателей уходят при ЛЮБОМ режиме журнала: режим управляет только
записью на диск. Пороги ниже приняты оператором (РЕШЕНО 19).

| `extra_missing` лишние и пропавшие | Стоп-заявки в QUIK с нашим тегом, которых нет в книге (лишняя: ручная из терминала, дубль после рестарта) и в книге armed, которых нет в QUIK (пропавшая: снята брокером, истекла) | лишняя > 10 с = WARN `STOP_UNKNOWN`; пропавшая: если срок вышел по `EXPIRY_DATE`/окну = INFO `STOP_EXPIRED` и книга -> expired; иначе CRITICAL `STOP_ORDER_WITHDRAWN` (флэш) | по коду | `observers.extra_missing` |

| `tx_rate` счётчик транзакций | Все транзакции через `Bridge` по классам A/B и потребителям (робот/ручные/доводка/стоп-заявки): за календарную секунду по часам, за 10 с, в минуту, за день; оценка штрафа (транзакции сверх порога брокера x 4 руб.) | > 70% потолка 5 с подряд = WARN `TX_RATE_NEAR`; ожидание класса A в очереди > 2 с = CRITICAL `TX_QUEUE_STALL`; штраф за день > 0 = WARN в отчёте | по коду | `observers.tx_rate` (счётчик всегда, флаг гасит тревоги) |
| `gap_wait` | Каждый вход/выход из `GAP_WAIT`: причина выхода (откат/убыток/время), цена, потери против немедленного рынка | всегда журнал; выход по убытку или времени = WARN `GAP_LIMIT_HIT` | по коду | `observers.gap` |
| `go_watch` | Потенциальное ГО по разделу 7 | 80% / 100% | WARN / CRITICAL | `observers.go` |
| `child_price` | Цена ребёнка после активации против `STOPPRICE` и подушки: QUIK поставил ту цену, что мы задали в `PRICE`/`SPREAD`? | отклонение >= 1 шаг | WARN `CHILD_PRICE_MISMATCH` | `observers.child_price` |
| `daily_report` | В 23:55 и в 06:55: число стоп-заявок поставлено/активировано/исполнено/снято/истекло, средние и максимальные t_act->t_seen->t_done, число расхождений по каждому наблюдателю, транзакции и штраф, ГО-пики, список незакрытых тревог | ежедневно | INFO в Telegram + строка в утренний SMS (готовый канал `stl-morning-sms`) | `observers.daily_report` |

Все тревоги наблюдателей с cooldown по (код, so_id) 60 с, чтобы не заспамить
Telegram при массовом расхождении.

## 11. Ограничитель частоты транзакций

Факт от оператора: брокер штрафует 4 руб. за каждую транзакцию сверх 15..20 в
секунду. Транзакции порождают все: роботы (заявки на баре, у N роботов один момент),
ручные заявки, стоп-заявки, доводка (каждый MOVE), гэп-доводка (MOVE за экстремумом),
снятия. Ограничитель один, глобальный, в единственной воронке `Bridge.Place`/
`Cancel`/`Move` + новые `StopPlace`/`StopKill`, так его нельзя обойти.

- Транзакция = ЛЮБАЯ постановка, снятие, перестановка (РЕШЕНО 20). Окно = календарная
  секунда по часам агента. Потолок `tx_rate_cap` = 10 транзакций за календарную
  секунду, ЖЁСТКО: счётчик обнуляется на границе секунды, 11-я ждёт следующей секунды.
  Burst сверх потолка нет: token bucket с запасом 5 давал бы до 15 за одну секунду,
  это уже порог штрафа. Пример: 12 роботов закрыли бар в 10:00:00.3: 10 уходят в эту
  секунду, 2 в 10:00:01; 20 роботов: последний вход в 10:00:01.
- Классы приоритета: A = выходы, стопы, снятия, kill-switch, эскалация к рынку,
  MOVE в `GAP_WAIT`; B = входы, перестановки режимов 2..4 входов, постановка
  стоп-заявок входа. Пустой bucket: A идёт первым, B ждёт. Kill-switch вне очереди
  (его снятия и так класса A, но он ещё и очищает очередь B).
- Сглаживание перестановок: если для одной заявки в очереди уже стоит MOVE, новый
  MOVE его заменяет (в рынок уходит последняя цена, а не вся история). Анти-дребезг
  200 мс из `execution.go` остаётся.
- Ожидание в очереди > 2 с для класса A = CRITICAL `TX_QUEUE_STALL` (что-то
  генерирует транзакции лавиной: смотреть счётчик по потребителям); B ждёт молча до
  10 с, затем отказ `TX_RATE_LIMIT` потребителю (робот увидит REJECT с причиной,
  доводка повторит на следующем тике).
- Daily cap (есть) остаётся вторым поясом.
- Штрафной счётчик: наблюдатель `tx_rate` считает по календарным секундам транзакции
  сверх 15 (нижняя граница порога брокера) и оценивает штраф 4 руб. за каждую.
- Порядок с разделом 19: NET_HOLD и WAIT_CROSS стоят ДО ограничителя. Удерживаемая
  заявка слот секунды не занимает; в bucket она входит при выпуске со своим классом.
  Время в WAIT_CROSS в тревогу `TX_QUEUE_STALL` не входит (свой наблюдатель `cross`).

Роботы с нативными стопами (раздел 13) удваивают транзакции на баре: kill стопа +
заявка + новая связка. При 12 роботах это 36 транзакций на одном баре: bucket
растягивает их на ~3.5 с. Приемлемо для M1, но это аргумент ставить связку только
при изменении уровня, а не каждый бар.

## 13. Роботы: нативные стопы вместе с ручными (РЕШЕНО 17)

Робот входит через intent (раздел 4). Защита позиции нативной связкой:
- раннер после каждого бара отдаёт агенту желаемую защиту `SetRobotProtection
  {robot_id, symbol, sl_price, tp_price, trail_offset}` (0 = нет). Уровни считает
  стратегия: у `make_on_bar` стоп `sl_frac` и тейк `tp_atr` уже известны на баре, у
  standalone (`us_open_fvg`) фиксированы от входа. Это правка `trader/lab`
  (`STLRuntime` протокол + `make_on_bar`), зона backtests: письмо владельцу; в
  бэктесте вызов no-op;
- агент держит ОДНУ связку `TAKE_PROFIT_AND_STOP_LIMIT_ORDER` на робота и инструмент
  с тегом `rr:<robot>:pr`, переставляет её только при изменении уровня на >= 1 шаг
  (KILL+NEW, класс B; `MOVE_ORDERS` для стоп-заявок сверить на GZ), при позиции 0
  снимает;
- филл связки приходит раннеру обычным `OrderUpdate` по префиксу `rr:` и меняет
  позицию (уже так); на следующем баре стратегия видит флэт и не повторяет выход;
- правило от двойного исполнения: перед ЛЮБОЙ заявкой робота X по инструменту агент
  снимает связку X и ждёт ack (класс A, ~1 с), только потом ставит заявку; после
  исполнения заявки связка ставится заново от новой позиции. Окно без защиты = время
  ack снятия + исполнение заявки; это тот же интервал, что сегодня без защиты вовсе;
- `exit_only` и `max_position` без изменений; связка не увеличивает позицию, Guard
  считает её как рабочий объём.

Транзакционная цена (раздел 11): на баре с изменением уровня 2 транзакции, на баре с
заявкой 3..4. Ставить связку каждый бар «на всякий случай» нельзя.

Плюс: стоп живёт при мёртвом раннере, агенте и терминале. Минус: число стоп-заявок и
транзакций; лимит числа стоп-заявок у брокера сверить (раздел 14).

## 14. Риски и ограничения

- Реальные деньги на этапе 1: проверки на GZ по 1 контракту, каждая серия = сделки
  туда-обратно с комиссией и спредом. Бюджет серии (контракты, рубли) утверждает
  оператор до запуска (В21). Kill-switch под рукой, `quik_trading_enabled` и
  белый список только GZ на время серии.
- Штраф за транзакции: 4 руб. за каждую сверх 15..20/с; ограничитель раздела 11,
  правило принято оператором: любая транзакция, календарная секунда (РЕШЕНО 20).
- Лимит числа стоп-заявок у брокера: сверить; роботы умножают их число.
- Клиринг и вечерняя сессия: живут ли стоп-заявки через 14:00/18:50 и ночь, что
  делает брокер на экспирации: сверить на GZ; `expiry_sync` ловит расхождение.
- Снятие брокером (margin call, служебное): `STOP_ORDER_WITHDRAWN`.
- Мёртвый агент + режим 2 на выходе = режим 1 (принято); мёртвый агент + гэп =
  ребёнок с подушкой висит: `AGENT_DOWN` из STL уже есть; при живом STL оператор
  снимает руками.
- Гэп-доводка ждёт откат на падающем рынке: три ограничителя раздела 5; наблюдатель
  `gap_wait` считает, сколько это стоило против немедленного рынка, чтобы через
  месяц пересмотреть значения по факту, а не по ощущению.
- Коллар агента 0.2% для MOVE от текущей цены ребёнка: при гэпе рынок дальше
  коллара, MOVE отвергнется; тогда `KILL` + `NEW_ORDER` по тачу (Guard, класс A).
- 32-битный QLua: номера стоп-заявок и epoch-ms только `%.0f`/`math.floor`.
- Поля `OnStopOrder` и транзакции различаются по именам и версиям QUIK у Финама:
  только GZ-серия решает.
- Капы агента к стоп-заявкам при постановке как к лимиткам; активная стоп-заявка в
  working как резерв. Пуш из STL только ужесточает.
- Наблюдатели сами транзакций не делают, но пишут журнал: диск VDS (ротация по дню,
  30 дней) и CPU на сверке каждые 2 с (десятки стоп-заявок, дёшево).
- Комиссия maker/taker и скальперская скидка в ledger: учётные задачи.

### 19.1 Термины

- Владелец: `rr:<robot>` (робот), `so:<id>` (ручная умная заявка), `recon`
  (align-заявка агента), пусто (заявка из терминала QUIK или приложения брокера:
  видна только через таблицу `orders` раз в 2 с, тег пуст).
- Встречная: заявка того же инструмента противоположной стороны, не терминальная,
  `restingQty > 0`. Заявка PENDING без order_num считается висящей по своей цене.
- Пересечение: покупка с ценой >= цены встречной продажи; продажа с ценой <= цены
  встречной покупки. Не пересекается: ждать не нужно, кросс QUIK не сработает.
- Ребёнок стоп-заявки (раздел 3) после активации = обычная заявка в `orders` с нашим
  тегом; ДО активации стоп-заявка в стакане не стоит и встречной не является. Агент
  берёт ребёнка под управление в CHILD_SEEN (раздел 6), до этого (<= 2 с) он агенту
  не известен: это слепое окно, закрывается правилом «отказ QUIK кросс = в очередь».
- Намерение: заявка робота, принятая агентом, но ещё не отправленная в Lua.
- Реальные и бумажные: бумажный робот на агенте (`AgentRuntime(paper=True)`)
  исполняется в раннере по close бара и в агент заявок не шлёт (проверено по
  `place_order`). Бумага не участвует ни в очереди, ни в зачёте автоматически.

### 19.2 Очередь встречных заявок (этап Q1, промежуточная мера)

в `recon.Order` стороны нет, возможно нужна колонка в `acc_ord` из Lua).

Правило. Запрос R (код, сторона, цена, владелец) ЖДЁТ, если есть встречная W другого
владельца, пересекаемая по цене, ИЛИ если встречная W того же инструмента ушла
(исполнилась/снята) в ТЕКУЩУЮ календарную секунду (правило оператора: в одну секунду
противоположные заявки по одному инструменту не исполняются). Встречная того же
владельца: снять её и ждать ack, как в разделе 6 (сегодня это делает раннер; после
Q1 раннерное ожидание 5 с можно не трогать, оно станет холостым).

Состояние WAIT_CROSS (в машине раздела 6 перед `NEW_ORDER`):

- вход: `OrderUpdate` PENDING с текстом `wait_cross:<владелец W>:<order_num W>`;
  раннер видит `submitted` (как сегодня), STL видит причину;
- выпуск: любое событие по W (`OnOrder` terminal, `OnTrade` до нуля, `OnTransReply`
  отказ, MOVE W на непересекаемую цену), граница календарной секунды, тикер 100 мс;
  повторная проверка всех ждущих по инструменту;
- при выпуске: повторно Guard.CheckPlace (working cap считается на момент отправки),
  затем `CommitPlace` и `bridge.Place`. Цена: заявки роботов маркетабельные (раннер
  считает по тачу ДО ожидания); после ожидания >= 1 с агент подтягивает цену к
  свежему тачу `md` (<= 5 с) только в агрессивную сторону (покупка вверх, продажа
  вниз) и только внутри коллара от исходной цены. Это поведение режима 1 (раздел 5)
  до появления intent. Стакан старше 5 с: отправить как есть;
- таймаут `cross_wait_max_ms` (В25, предложение 5000 = как у раннера):
  - R = выход (`purpose=EXIT`, этап Q2) и W = вход робота (класс B): снять W
    (KILL, класс A), дождаться ack, отправить R. Владелец W получает CANCELLED с
    текстом `cross_yield:<владелец R>`; его стратегия повторит вход на следующем
    баре (так уже работает после любого снятия). Вопрос В26;

### 19.3 Внутренний зачёт (этапы N1..N2, целевой)

Смысл: робот A хочет купить N, робот B в то же окно продать M по тому же
инструменту. min(N, M) сводятся внутри платформы, на биржу уходит только нетто.
Счёт при этом не платит спред и сборы на сведённых контрактах и не порождает
транзакций.

Границы v1:

- участники: только реальные роботы `rr:` между собой. Никогда: бумага (в агент не
  попадает), `so:`, `recon`, заявки из терминала, дети стоп-заявок (уже на бирже);
- только намерения, ещё НЕ ушедшие в Lua. Зачёт против уже висящей на бирже своей
  заявки = этап N3 (гонка KILL/филл, откат внутренней ноги), не в v1;
- один инструмент, один счёт (у агента один `ManagerConfig.Account`);
- обе стороны проходят Guard.CheckPlace ДО зачёта, как перед отправкой: капы
  per-order/working/белый список/master-flag действуют и на внутренний филл. Daily
  cap не тратится (транзакции нет);
- `max_position` и `exit_only` живут в раннере до отправки и не меняются.

Окно удержания NET_HOLD: намерение робота удерживается `net_hold_ms` (В27,
предложение 300) до отправки, чтобы встречные намерения того же бара успели
прийти (роботы считают один и тот же close бара с разбросом миллисекунд). Ручные
заявки не удерживаются. Если bucket ограничителя (раздел 11) занят, удержание
бесплатно: заявка и так ждала бы. Класс A тоже удерживается: 0.3 с при баре M1 в
бюджете, а «A выходит из лонга, B входит в лонг» самая частая пара.

Раунд матчинга по инструменту в конце окна: покупки и продажи FIFO по времени
прихода (ничья по client_id), k = min(сумма покупок, сумма продаж), ноги режутся по
целым контрактам. Одна цена P на раунд для всех ног (тогда сумма денег ног = 0
точно). Остаток каждого намерения (N - k_i) уходит в WAIT_CROSS -> `NEW_ORDER` под
тем же client_id.

Цена P, только на сетке шага (РЕШЕНО 5, раздел 8):

1. last из `md`, если биржевое время сделки <= 5 с и bid <= last <= ask при свежем
   стакане (<= 5 с). Обе стороны получают цену рынка «как есть»;
2. иначе при свежем стакане: тач стороны ПОЗДНЕГО намерения (позднее купить: ask;
   позднее продать: bid). Позднее намерение платит то, что заплатило бы на бирже
   (тейкер), раннее получает улучшение на спред (мейкер). Это зеркало биржевой модели
   maker/taker; середина спреда отвергнута: она вне сетки;
3. ни ленты, ни стакана свежее 5 с, или `exchange_lag_ms` >= 5 с (реплей ленты после
   рестарта QUIK, см. память «QUIK Restart Tape Replay»): зачёта нет, оба намерения
   в WAIT_CROSS и на биржу. Внутренний филл без цены рынка не существует.
   Вопрос В28.

Доставка в раннеры (проверено по `runtime.on_order_event`): дедупликация филлов
суммирует по client_id (`already`) и режет по объёму ордера (`cap = u.quantity`,
`by_order[order_id]`). Отсюда правила:

- внутренняя нога: `OrderUpdate{client_id = исходный cid, order_id = "xn:<pair_id>",
  quantity = N, filled = k, state = PARTIAL (k < N) | FILLED (k = N), price = P,
  text = "xnet:<pair_id>:<другой робот>", ts_unix_ms = время раунда}`;
- биржевой остаток: обычные `OrderUpdate` c `order_id` = QUIK order_num, но
  `quantity = N` и `filled = k + filled_биржа` (накопительно по намерению; в
  `workingOrder` поле `preFilled = k`, `emitOrderUpdate` прибавляет его; `wo.qty`
  остаётся N - k, чтобы `restingQty`/working cap считались верно: ПРОВЕРИТЬ по
  `totalWorkingLocked`). `price` = VWAP ТОЛЬКО биржевой части: раннер книжит свежие
  контракты по `u.price`, смешанный VWAP исказил бы среднюю;
- раннер: `_apply_fill` берёт `taker_points` с каждого филла; для `order_id` с
  префиксом `xn:` сбор = 0 (В29). Правка `robot_runner/runtime.py`, зона real-trade.
  Филл с `order_id xn:` попадает в `_fills`, `runner_state.json`, `recent_fills`
  статуса и в зеркало STL без других правок;
- инвариант доставки: повторная доставка любой ноги идемпотентна (already по cid,
  cap по order_id), поэтому агент вправе перефанить журнал после рестарта.

### 19.4 Источник истины после зачёта

Сегодня истина одна: QUIK. Позиция робота выводится из его филлов, филлы сверяются
со сделками QUIK по тегу brokerref в обе стороны (`recon.evalTrades`), потерянные
филлы восстанавливаются из таблицы сделок (`runner/journalsync.go`). Внутренняя нога
сделки QUIK не имеет: без смены источника истины recon объявит MISMATCH на каждый
зачёт, а ledger не увидит половину торговли робота.

Что ОСТАЁТСЯ истиной от QUIK (не меняется):

- позиция счёта по инструменту (`futures_client_holding`, acc_pos);
- биржевые сделки (`acc_trd`, `OnTrade`), в том числе по нетто-остаткам;
- деньги, ВМ, комиссия брокера (`futures_limits`, `ts_comission`);
- рабочие заявки (`orders`).

Что ПЕРЕСТАЁТ быть истиной:

- «позиция робота = сумма его сделок QUIK по тегу»;
- «филл робота <=> сделка QUIK с его тегом» (двусторонняя сверка `evalTrades`);
- «сделка QUIK по тегу без филла в книге = потерянный филл» остаётся верным, но
  обратное «филл без сделки QUIK = фантом» верно только для биржевых филлов.

Новый источник истины для атрибуции по роботам: журнал зачётов на агенте.

- Файл `<data_dir>/xnet/xnet-YYYYMMDD.jsonl` (тот же `RobotsDataDir`, что и
  `runner_state.json`), append-only, одна JSON-строка на запись, fsync на каждую
  запись, ротация по дню, хранить 90 дней. Пишется ДО фана `OrderUpdate` (write-ahead).
- Запись `pair`:
  `{kind:"pair"|"shadow", pair_id:"<epoch_ms>-<seq>", ts_ms, exch_ts_ms, code, price,
  qty, price_src:"last"|"touch", bid, ask, last, legs:[{robot, client_id, side,
  qty}], rest:[{client_id, qty}]}`. Ног в v1 ровно две; qty ног равны; сумма
  подписанных qty = 0; сумма side*qty*price = 0.
- Запись `rest`: `{kind:"rest", pair_id, client_id, order_num}` когда QUIK присвоил
  номер биржевому остатку: связь внутренней ноги с биржевыми сделками нетто.
- Запись `replay`: `{kind:"replay", pair_id, at_ms}` при повторном фане после
  рестарта (диагностика, не данные).
- Идентификаторы: `pair_id` уникален на агенте; `order_id` ноги в книге робота =
  `xn:<pair_id>`; dedup_key в ledger = `x:<pair_id>:<robot>`.
- Восстановление после рестарта агента: прочитать журнал текущего дня, перефанить
  все ноги `pair` (идемпотентно, 19.3), записать `replay`. Рестарт QUIK журнал не
  трогает. Рестарт раннера: `runner_state.json` уже хранит ноги; недостающие
  дофанит агент (`netsync`, ниже).
- Зеркало в STL: новый кадр `XNetReport{pairs[]}` (proto, зона real-trade) на каждую
  запись и весь день при реконнекте; STL хранит в таблице `algo_xnet` (бэкап и
  экраны). Первичен файл агента; копия STL нужна для восстановления файла, если VDS
  потерян, и для сверки «журнал против QUIK» из STL.

Новые инварианты (проверяются наблюдателем `xnet` каждые 10 с и на экране сверки):

- I1 по инструменту: сумма книг реальных роботов + нетто ручной торговли (классы
  `terminal`/`smart`/`recon` из `status/daypnl.go`) == позиция счёта QUIK. Сегодня
  позиция «контекстна» (recon.go, шапка); после зачёта её надо ПОКАЗЫВАТЬ как
  тождество с остатком, WARN `POS_IDENTITY` при остатке != 0 дольше 60 с. Шага
  align не порождает.
- I2 по роботу: книга == биржевые сделки QUIK с его тегом + его ноги журнала
  зачётов. Хвост раннера (`recent_fills`) это кэш, восстанавливаемый из этих двух
  источников.
- I3 по паре и по инструменту за день: сумма подписанных контрактов внутренних ног
  == 0 и сумма подписанных денег == 0 (одна цена на раунд).
- I4 денежный: сумма реализованного по всем роботам за жизнь позиций == реализованное
  счёта по биржевым сделкам (при закрытых позициях). Цена P только перераспределяет
  результат между A и B и не меняет сумму: A платит k*P, B получает k*P.
- I5 комиссия: биржевой сбор счёта по QUIK == сбор по биржевым филлам роботов +
  ручные; внутренние ноги в сбор не входят (сбор 0 в книге, В29).

Кто «прав» при расхождении:

| Расхождение | Прав | Действие |
|---|---|---|
| I1: сумма книг + ручные != QUIK | QUIK | найти робота через I2; шага align нет |

### 19.5 Риски зачёта

- Одна нога внутренняя, биржевой остаток не налился/налился частично: штатно,
  остаток = обычная заявка (WAIT_CROSS -> рынок -> режимы раздела 5); внутренняя
  нога окончательна, раннер видит PARTIAL и живёт дальше.
- Падение агента между записью пары и фаном: write-ahead + перефан при старте,
  идемпотентность на стороне раннера. Падение между матчингом и записью: пары нет,
  оба намерения потеряны как при любом падении агента до `bridge.Place` (раннер
  повторит на следующем баре).
- Падение раннера после фана до `persist`: `netsync` дофанит из журнала (как
  `journalsync` для биржевых).
- Реплей ленты после рестарта QUIK: `exchange_lag_ms` >= 5 с = зачёта нет (19.3, п.3).
- Цена P «нечестна» к одному роботу на величину спреда (правило 2): сумма не
  меняется (I4); наблюдатель `xnet` копит «улучшение» по роботам, через месяц видно,
  кого правило системно кормит.
- Два робота одной стратегии на противофазе: зачёт спрячет пилу за нулём транзакций.
  Счётчик `netted_ratio` по роботу в отчёте дня; высокий = вопрос к отбору роботов, не
  к зачёту.
- Бэктест считает тейкера на каждом филле; вживую внутренняя нога без сбора и без
  спреда: реал лучше модели, а не хуже. Ledger хранит `commission_saved_rub` по
  модели (отчёт), не в net.
- Заявка из терминала оператора зачёту не видна и в него не входит; очередь её
  видит через `orders` с задержкой до 2 с (слепое окно, закрывается правилом «отказ
  кросс = в очередь»).
- Kill-switch: NET_HOLD и WAIT_CROSS очищаются с отказом `blocked`; пары, уже
  записанные, остаются.
- Журнал: диск VDS. Ротация по дню, 90 дней; копия в STL `algo_xnet`; наблюдатель
  `xnet` пишет CRITICAL на ошибке записи и выключает зачёт (без журнала внутренних
  филлов не бывает).

### 19.6 Экономия транзакций и денег

- Транзакции: очередь убирает отклонённые кросс-заявки (каждая = транзакция; 15.09
  одна). Зачёт убирает по одной транзакции на каждое ПОЛНОСТЬЮ сведённое намерение
  (при остатке транзакция всё равно одна). При 4 роботах RI на баре это 0..4
  транзакции в секунду; штраф брокера начинается с 15..20/с, то есть штраф зачёт
  почти не трогает, а его ценность в другом: спред, сборы, отсутствие кросс-отказов
  и проскальзывания через бар (15.09: 13 x 20..40 п.).
- Деньги на сведённый контракт: спред (RI 1 шаг = 10 п.) плюс два биржевых сбора
  (`commission_for` по группе: index 0.0000660 x номинал на сторону) плюс два
  брокерских (0.45 руб. на сторону по памяти проекта, ПРОВЕРИТЬ в `commission.py`).
  Номинал по коэффициенту из params-фида, в документе не считаем.
- Отчёт дня наблюдателя `xnet`: пар, контрактов, транзакций и рублей по модели
  «сколько бы стоило на бирже».

### 19.8 Тестовый план (детерминированный, fake bridge/book/clock)

Go `internal/trade`:
- гейт: пересечение есть/нет по обеим сторонам; PENDING без номера считается
  висящей; та же секунда после ухода W = ждать до границы; выпуск по filled /
  cancelled / reject W / MOVE W; повторный Guard при выпуске; подтяжка цены к тачу
  только в агрессивную сторону и внутри коллара; стакан > 5 с = как есть;
- таймаут: EXIT против входа робота = KILL W, ack, отправка R, CANCELLED W с
  `cross_yield`; ENTRY = REJECT `CROSS_WAIT_TIMEOUT` с client_id и без транзакции; W из
  терминала никогда не снимается; kill-switch чистит очередь;
- отказ QUIK «кросс» на отправленной заявке = возврат в WAIT_CROSS, общий таймер;
- MOVE в пересечение удерживается, > 1 с отбрасывается;
- матчер: FIFO-раскладка, k = min, остатки; цена по трём ветвям и отсутствие
  зачёта при несвежих данных; свойство на случайных раундах: I3 (контракты и
  деньги в ноль), все цены на сетке;
- доставка: последовательность `OrderUpdate` внутренняя нога + биржевой остаток с
  накопительным `filled`, `preFilled` не ломает `restingQty`/working cap;
- журнал: write-ahead до фана, перефан после «рестарта» идемпотентен, битая
  последняя строка (обрыв записи) терпится, остальные читаются; ошибка записи =
  зачёт off + CRITICAL;
- сценарий 15.09: таймлайн trans 1077/1078/1079, ожидаемо: 1079 не отправлена, выпуск
