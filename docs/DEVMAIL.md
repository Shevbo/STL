# Почта окон: доставка в живую сессию

## Что чинили

До 12.08.2026 письмо, пришедшее в СЕРЕДИНЕ сессии, окно не видело до следующего
запуска. 11.08 письма пролежали 7 и 30 часов при работающих окнах. Причина не в
почте, а в последней миле: будильник висел на `SessionStart`, а сессия живёт
десятками часов. Сама почта (`/api/v1/dev/msg`, `ack`, просрочка, крон-алерт
оператору) работала правильно и осталась как есть.

## Как устроено сейчас

```
хостер                          машина окон
──────                          ───────────
agent_control (источник правды)
   ^                            devmail_sync.py   раз в 45 с, ssh, ФОН
   └── /api/v1/dev/inbox/<окно> ───────> ~/.stl-devmail/<окно>.json
                                              ^
                                devmail_hook.py  на КАЖДЫЙ ввод, ~48 мс,
                                              БЕЗ сети, только чтение файла
```

Транспорт и чтение разделены намеренно. Пока за письмами ходил сам хук, показ
почты стоил ssh-рукопожатие (замерено 1.8 с), поэтому висеть на каждом вводе он
не мог. Теперь по сети ходит только фон, а хук читает готовый файл.

## Цена в токенах

Это, а не секунды, было настоящим возражением против хука на каждый ввод.
Поэтому вывод трёхрежимный:

| Ситуация | Что печатает | Цена |
|---|---|---|
| ящик пуст | ничего | 0 токенов |
| пришло новое | полный текст, максимум 5 писем, тело до 700 символов | один раз на письмо |
| показано, ack нет | одна строка с id | не чаще раза в 30 минут |

Микропромпт (кто ты, какая зона, что делать с письмом) печатается только на
`SessionStart`: свежей сессии он нужен, на каждом вводе это чистый расход.

## Установка на машине окон

Машина окон — Windows 10 VM (VS Code Local) рядом с vibe. Снаружи в неё никто не
ходит, поэтому службу ставит то самое окно, которое там и живёт: открой окно и
выполни у себя одну команду.

Хуки уже лежат в `.claude/settings.json` репозитория, ставить их руками нечего.

```bash
STL_WINDOW=real-trade bash scripts/devmail_install.sh
STL_WINDOW=backtests  bash scripts/devmail_install.sh
STL_WINDOW=ui-ux      bash scripts/devmail_install.sh
```

Установщик сам определяет систему:

| Система | Чем крутится фон | Автозапуск |
|---|---|---|
| Windows (Git Bash / MSYS) | задание планировщика `STL-DevMail-<окно>`, раз в минуту | планировщиком |
| Linux / macOS / WSL | строка crontab, раз в минуту | кроном |

Демона нет намеренно. Первая версия поднимала фоновый цикл через `nohup` и
стерегла его pid-файлом: на Windows это ломается, а на Linux демона всё равно
надо воскрешать после перезагрузки. Планировщик делает и то и другое сам.

Интерпретатор ищется (`python3`, `python`, `py`), а в задание Windows
подставляется его АБСОЛЮТНЫЙ путь: у задания свой PATH, и `python3` там может
не разрешиться — задание падало бы каждую минуту молча.

Каждое окно Claude запускается с переменной `STL_WINDOW`, равной своему имени.
Без неё хук молчит и ничего не ломает.

Снять на Windows: `schtasks //Delete //TN STL-DevMail-<окно> //F`.
Снять на Linux: убрать строку `devmail_sync.py --window <окно>` из `crontab -e`.

## Проверка, что работает

```bash
# 1. положить письмо
ssh hoster 'bash ~/apps/shectory-trader/scripts/devmsg.sh send real-trade "тест" "проверка" backtests'
# 2. дождаться фона (до 45 с) и посмотреть, что увидит окно
STL_WINDOW=real-trade python3 scripts/devmail_hook.py <<< '{"hook_event_name":"UserPromptSubmit"}'
```

## Когда что-то не так

Хук НИКОГДА не молчит про сломанный фон: слепок старше 5 минут — и он пишет
«ПОЧТА НЕ СИНХРОНИЗИРУЕТСЯ». Пустой ящик и мёртвый синк должны выглядеть
по-разному, иначе окно уверено, что писем нет.

Лог фона: `~/.stl-devmail/sync-<окно>.log`. Перезапуск: та же команда установки.

## Что осталось прежним

- Источник правды — `agent_control` на хостере. Слепок ничего своего не хранит.
- `ack` по-прежнему через `POST /api/v1/dev/msg/<id>/ack`. Пока не подтверждено,
  письмо считается непрочитанным.
- Просрочка (4 часа) и крон-алерт оператору в Telegram — как были. Эскалация
  обязана уходить ИЗ застрявшего контура: если стоят все три окна, печатать
  тревогу внутрь них бесполезно.

## Чего не делать

Не выводить признак «прочитано» сканированием хвоста журнала. У Lineman это
11.08 дало экспоненциальную петлю: окно источника длиннее окна ответов, старое
сообщение снова считается неотвеченным, каждый ответ вымывает окно дальше —
256 записей за 4 минуты. Факт прочтения должен лежать в состоянии, а не
выводиться из журнала.
